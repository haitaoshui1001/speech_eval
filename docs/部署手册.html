演讲评分系统 · 云服务器部署手册

目标机器：阿里云 ECS 2 vCPU / 2 GiB / 40 GiB ESSD / 固定带宽 3 Mbps 部署形态：systemd 跑 uvicorn 单进程 + nginx 反向代理，用 公网 IP + HTTP 访问，不要域名和证书。

本手册里的命令都可以直接照抄——这份 HTML 生成时已填入公网 IP <公网IP> 与发布包日期 20260928。Markdown 源（deploy/部署手册.md）里仍写作占位符；换服务器时用 python tools/build_html.py --ip 新地址 --date 新日期 重新生成本页即可。

0. 先看这一段：整体形态与为什么这样部署

四条不能改的硬约束（改了就坏）：

约束 原因
uvicorn 只能单进程 分析任务状态、并发信号量、SQLite 连接都在进程内。多 worker 会出现"进度页查不到任务"、并发限制失效、SQLite 写冲突。install.sh 会检查 unit 里出现 --workers 就中止。
不能用 ProtectHome=true / ProtectSystem=strict 应用会把配置写回代码目录（.env、提示词.json）。strict 沙箱下网页里改设置会保存失败。
ASR_ENGINE 必须保持 qwen 换成本地 whisper（small 约 +2GB）会立刻打爆 2 GiB 内存。
client_max_body_size 必须 ≥ MAX_VIDEO_MB nginx 默认 1 MB，会在应用之前返回 413，症状是"上传大视频直接失败，日志里没有任何应用记录"。install.sh 会自动对齐。

这台机器的真实上限：内存不是瓶颈（实测应用 2 并发峰值约 500–600 MB），3 Mbps 出网（约 375 KB/s）才是。两个人同时在线回看视频会明显卡顿，这是带宽决定的，不是配置能优化的。详见第 10 节。

1. 服务器准备（阿里云控制台，5 分钟）

1.1 装系统

必须是 Ubuntu 22.04 64位。

  • ❌ 不要用 Ubuntu 20.04（自带 Python 3.8，本项目要求 ≥ 3.10，install.sh 会直接报错退出）
  • ❌ 不要用 Alibaba Cloud Linux / CentOS（脚本里的包名、路径按 Debian 系写的）
  • 重装系统入口：控制台 → 实例 → 更多 → 云盘和镜像 → 更换操作系统（会清空系统盘，做之前先备份 data/，见第 9 节）

登录方式选"密钥"或"密码"都行，下面命令按 root 用户写。

1.2 安全组（最容易漏的一步）

控制台 → 实例 → 安全组 → 管理规则 → 入方向 → 手动添加：

端口 授权对象 说明
22/22 建议改成你自己办公网络的固定 IP 段 SSH。放 0.0.0.0/0 会被全网爆破，能收紧就收紧
80/80 0.0.0.0/0 用户访问端口
8000/8000 不要加 uvicorn 只监听 127.0.0.1，它不该对公网开放；开等于绕过 nginx 的体积限制和安全响应头

只有当你用 --no-nginx 部署时，才需要放行 --app-port 指定的那个端口。

1.3 登录并确认机器规格

bash
ssh root@<公网IP>

# 三条确认命令，输出应当分别是 2、约 2Gi、约 40G
nproc
free -h | head -2
df -h / | tail -1

2. 在本地 Windows 上打发布包

git 远端只用于代码备份与异地容灾：服务器上没有仓库凭据，/opt/speech-assist 也不是 git 工作树（它由 rsync 出来，且 .env / api_key.txt / data/ 本来就在 git 之外），所以服务器上没法靠 git clone / git pull 完成部署。发布链路是「本地打包 → scp 上传 → 解压 → 安装脚本」，日常升级走第 8 节。

在你自己的 speech_assist 目录里，用 PowerShell：

powershell
cd d:\heyun\speech_assist
powershell -ExecutionPolicy Bypass -File deploy\package.ps1

产出：dist\speech-assist-20260928.tar.gz，实测 3.37 MB / 52 个文件（体积几乎全来自 tests/sample_speech.mp4，带上它是为了装完能在服务器上直接跑自检；包根另有 BUILD_INFO.json 版本指纹，见 §8 与 §11）；-SkipTests 时约 0.2 MB 以内。

脚本做四件事，都是为了避开已知坑：

  1. 白名单打包：只带 app/ deploy/ docs/ tests/ requirements.txt 评价标准.txt .env.example。 api_key.txt、.env、data/ 一定不进包 —— 否则要么把千问密钥传到公网机器上，要么把本地开发用的 SECRET_KEY / admin123 盖到服务器上，要么覆盖真实用户数据。
  2. 换行符归一为 LF：deploy/*.sh、speech-assist.service、nginx-speech-assist.conf、env.production。Windows 上写的 bash 脚本带 CRLF，在 Linux 上会报 /usr/bin/env: bash\r: No such file or directory，这是最常见的"脚本第一步就跑不起来"。
  3. 回环校验：打完立刻解压一次，确认中文文件名 评价标准.txt 没被编码破坏（它被应用硬编码引用，缺了就直接起不来），并确认脚本里没有残留 CR。 实测确认包名以 UTF-8 存储（包内找不到 GBK 编码的文件名字节），所以 Linux 上 tar xzf 解出来是正常中文名；tar -tzf 在 PowerShell 里显示成乱码只是控制台代码页问题，不是包的问题。
  4. 版本指纹：打包前从 git 取短 sha、分支与脏标记，写成包根的 BUILD_INFO.json，并在末尾打印。升级后 /health 的 version 应等于它（第 8 节的 update.sh 会自动对账）。取不到 git（比如手工拷出去的目录）会记 unknown 并照常打包——指纹是诊断信息，不拦发布。

可选参数：

powershell
# 换输出目录
powershell -ExecutionPolicy Bypass -File deploy\package.ps1 -OutDir D:\release
# 不带 tests/（服务器上不打算跑自检时用）
powershell -ExecutionPolicy Bypass -File deploy\package.ps1 -SkipTests

3. 上传、安装、填密钥（服务器上，约 10 分钟）

3.1 上传发布包和密钥

在本地 PowerShell 里（api_key.txt 单独传，因为它不在发布包里）：

powershell
cd d:\heyun\speech_assist
scp dist\speech-assist-20260928.tar.gz root@<公网IP>:/root/
scp api_key.txt root@<公网IP>:/root/

api_key.txt 里就是你的阿里云百炼（DashScope）API Key，一行即可。

3.2 解压并安装

在服务器（SSH 会话）里：

bash
cd /root
tar xzf speech-assist-20260928.tar.gz
cp /root/api_key.txt speech-assist-20260928/       # install.sh 会自动放进 /opt 并 chmod 600
cd speech-assist-20260928

sudo bash deploy/install.sh

想自己定管理员口令（不指定则随机生成并只打印一次）：

bash
sudo bash deploy/install.sh --admin-password '你的管理员口令'

口令里有 # 时值得知道（都是实测）：# 紧跟字符（My-Pw#2026）能原样读回，# 前面有空格或制表符（a #b）会被 dotenv 当成行内注释、口令静默变成 a；值里带引号且不成对（"ab）会让整行解析失败、键直接消失。install.sh 遇到第一种情况会自动加引号写回（引号被剥掉、口令原样生效），遇到无法安全表达的情况会打印 [注意] 让你换口令。

--admin-password / --admin-user 只在 .env 里那两项还是占位符或默认值时生效。装完再跑一次并带上它们不会改口令也不会改名（会明确打印「未生效」）——改口令的唯一入口是登录后的 /settings（保存时回写数据库哈希），忘了口令的救法见 §11.1。

install.sh 依次做的事：

步骤 内容
同步代码 rsync -a --delete 到 /opt/speech-assist，--delete 保证删掉的文件真被删；.env / api_key.txt / data/ / .venv / 提示词.json 在 exclude 列表里，既不被覆盖也不被误删
断言 app/ 与 评价标准.txt 必须存在，否则中止
系统依赖 apt-get install python3-venv、ffmpeg、nginx、rsync、curl、openssl 等
pip 源 能解析到 mirrors.cloud.aliyuncs.com 就走阿里云内网源（不占那 3 Mbps 公网出口）
swap 内存 < 4 GiB 且无 swap 时建 2 G /swapfile，写 /etc/fstab，vm.swappiness=10。这是 OOM 保险，不是性能手段
运行账号 建 speech 系统用户（nologin）
venv /opt/speech-assist/.venv + pip install -r requirements.txt，并断言 Python ≥ 3.10
.env 用 deploy/env.production 生成，随机 SECRET_KEY（64 位十六进制）、填管理员口令；已存在则只补占位符，不覆盖你改过的值
权限 目录 755 / 文件 644 / .env 与 api_key.txt 600，属主 speech；.venv 被 prune 掉以免打回可执行位
systemd 渲染 speech-assist.service 到 /etc/systemd/system/，daemon-reload + enable
nginx 渲染到 /etc/nginx/conf.d/speech-assist.conf，移除 Ubuntu 自带的 default 站点（它会抢 80 端口的默认服务器），nginx -t 通过后 restart
ufw 如果启用了本机防火墙，放行对外端口
验收 最多等 30 秒轮询 http://127.0.0.1/health，通过则打印模式/ffmpeg/自动压缩目标/并发等实况

脚本是幂等的：跑第二遍不会动你的 .env、api_key.txt、data/，venv 只补装差异依赖。

3.3 常用变体

bash
# 80 被占用 / 不想用 80
sudo bash deploy/install.sh --listen-port 8080

# 不要 nginx，让 uvicorn 直接监听 0.0.0.0:8080（此时安全组要放行 8080）
sudo bash deploy/install.sh --no-nginx --listen-port 8080

# 装到别的目录 / 换应用内部端口
sudo bash deploy/install.sh --app-dir /data/speech-assist --app-port 8123

# 已看过帮助
sudo bash deploy/install.sh --help

4. 验收清单（照着勾，全部通过再交付）

4.1 机器验收（30 秒）

bash
curl -s http://127.0.0.1/health | python3 -m json.tool

逐项对照：

字段 期望值 不对时
mode real 是 mock → 报告是演示数据。检查 api_key.txt 是否存在且 chmod 600 可读，然后 systemctl restart speech-assist
key_source api_key.txt（或 DASHSCOPE_API_KEY） none → 密钥没到位
ffmpeg true false → apt-get install -y ffmpeg 后重启服务。它同时是抽帧与自动压缩的硬依赖：compress_target_mb 不为 0 而 ffmpeg 缺失时，超过目标的视频会在压缩这一步直接报错（不会静默按原体积分析）
compress_target_mb 50 0 → 自动压缩已关闭，超过 MAX_VIDEO_MB 的照样拒收、没超过的原样入库。想改就在 /settings 的「站点」区改「自动压缩目标」，保存即生效
face_metrics true false → 人脸层降级，分数仍出，只是少了表情/朝向这类交叉核对指标。旁边会带一句 face_metrics_note 说明原因（装到 opencv-python-headless 5.x 是最常见的一种，pip install 'opencv-python-headless>=4.10,<5' 后重启即可）
rubric 你的评分标准摘要 报"缺失" → 评价标准.txt 没进包
version 本次打包时 package.ps1 末尾打印的短 sha（形如 26b04cb1f·main，脏工作区会挂 +dirty） 与本次包不符 → 传错包或 rsync 没生效（第 8 节的 update.sh 会自动做这道对账）；unknown → 包里没有 BUILD_INFO.json（旧包），升级一次即可补上
asr_engine_label 千问转录 显示 whisper → 这台机器上必须改回 qwen
concurrency.analyzers 2 与 .env 的 MAX_ANALYZERS 不一致说明改完没重启

/health 里含模型名与 token 用量，nginx 已把它限成 只有 127.0.0.1 能访问。从公网 http://<公网IP>/health 应当拿到 403，这是对的。

4.2 服务与端口

bash
systemctl status speech-assist --no-pager          # Active: active (running)，enabled
ss -ltnp | grep -E ':(80|8000)\b'
# 期望：0.0.0.0:80 由 nginx 持有；127.0.0.1:8000 由 uvicorn 持有，**不是 0.0.0.0:8000**
journalctl -u speech-assist -n 60 --no-pager       # 无 Traceback

4.3 人验收（用浏览器）

  1. 电脑 Chrome 打开 http://<公网IP>/ → 应重定向到登录页（打不开 = 安全组没放行 80）
  2. 用管理员账号（默认用户名 admin，口令见安装输出或 /opt/speech-assist/.env 的 ADMIN_PASSWORD）登录 → 落到 /admin
  3. /admin 里新建一个普通用户 → 用新账号登录 → 上传一段 1–2 分钟视频 → 进度页走完 → 报告有真实分数与改进建议
  4. 上传一个 超过 MAX_VIDEO_MB（这台 2C2G 生产机上是 200 MB，env.production 的收紧值；应用出厂默认 500） 的文件 → 应看到应用自己的"文件过大"提示，而不是 nginx 的 413 空白页。看到 413 说明 client_max_body_size 与 .env 没对齐
  5. 再上传一个 超过 COMPRESS_TARGET_MB（默认 50 MB）但没到上限 的文件 → 进度页会先走到「自动压缩到目标体积」，页头标出"原始 XX MB，已自动压缩"；报告页体积后带"（压缩前 XX MB）"，质控记录里写明压到多少、码率多少。这一步是验收压缩链路，最省事的测法是手机录一段 4K 或长时间视频
  6. 手机用 移动数据（不要连家里 WiFi） 访问同一地址，重复第 3 步 —— 这一步同时验收移动端适配和真实公网带宽体验

4.4 上线后必做

  • 改管理员口令：必须登录后在 /settings 改（保存时会把新哈希回写数据库）。 直接编辑 .env 的 ADMIN_PASSWORD 再重启是不生效的 —— init_db 只在管理员账号不存在时用它建号，口令哈希存在数据库里。忘了口令见第 11 节末尾的救法。
  • 自助注册是关闭的：访问 /register 会被送回登录页并提示"账号由管理员统一开通"。给用户开号在 /admin：单个新建，或下载 Excel 模板批量导入
  • 立刻备份一次：bash /opt/speech-assist/deploy/backup.sh
  • 配上每日备份（第 9 节）

5. 日常运维命令

bash
S=speech-assist

systemctl status $S --no-pager            # 状态 + 最近日志
systemctl restart $S                      # 改完 .env 里非热生效项后用
journalctl -u $S -f                       # 实时日志
journalctl -u $S --since "10 min ago" --no-pager

nginx -t && systemctl reload nginx        # 改 nginx 配置：先 -t 再 reload（reload不断流）
tail -f /var/log/nginx/speech-assist.access.log
tail -f /var/log/nginx/speech-assist.error.log

free -h && df -h /opt/speech-assist       # 内存与磁盘
du -sh /opt/speech-assist/data/*          # 数据目录分别多大

改配置有两种做法：

改什么 怎么做
大部分参数（模型、帧策略、并发、超时、开关、提示词、评分标准） 登录后在 /settings 网页改，保存即写回 .env 并热生效
WEB_THREADS 进程启动时读取，必须 systemctl restart speech-assist
DATA_DIR / ENV_FILE 同上，重启（换独立数据盘时见第 7.3 节）
端口 / 反代结构 改 /etc/systemd/system/speech-assist.service 或 /etc/nginx/conf.d/speech-assist.conf，然后 daemon-reload + nginx -t + restart
SECRET_KEY 可以换，但换完所有人登录态失效，需要重新登录
TTS_VC_MODEL 可以换（换完立即生效），但换的那一刻起所有已建好的复刻音色全部判作废：页面会显示"要重做"，学生重做一次即可。旧音色不会自动去远端删除，要清就得让学生自己点删除
VOICE_CLONE_ENABLED 填 0 只是关掉入口（报告页复刻节整段隐藏、授权/创建/删除三个 POST 一起拒绝），不会删掉任何已授权记录或已建好的音色；填回 1 后学生原来的音色照样能用，删除权始终在学生自己手里

手工改 .env 时不要改成 CRLF，也不要引入 BOM；应用会尽量兼容，但没必要制造变量。

6. 开机自启、宕机自愈、任务恢复

已在 unit 里配好，无需操作：

  • Restart=always + RestartSec=3：进程崩了 3 秒后自动拉起
  • systemctl enable：开机自启（install.sh 已做）
  • TimeoutStopSec=30 + SIGTERM：优雅停止
  • 停止/重启时正在跑的分析任务，会在下次启动时被 reset_stale_jobs() 标成"已中断"，用户在进度页点重试即可 —— 这是设计行为，不是数据丢失

想验证自愈能力（低峰期做）：

bash
kill $(pgrep -f 'uvicorn app.main:app')     # 杀掉进程
sleep 6 && systemctl is-active speech-assist # 应为 active

7. 磁盘与数据（这台机器最需要盯的东西）

系统盘 40 GiB。安装完成后：系统 + nginx + venv + ffmpeg 约占 6–8 GiB，可用大约 30 GiB。

7.1 什么在吃磁盘

一个视频会落两份：

位置 内容 体量
data/videos/ 上传的视频（用于回看与下载）。超过 COMPRESS_TARGET_MB 的已经是压缩后的 MP4，原件在压缩成功那一刻就删了 ≈ min(原文件, COMPRESS_TARGET_MB)
data/artifacts/<视频id>/ audio.wav + 最多 FRAME_COUNT_MAX 张关键帧 + cover.jpg 每视频约 5–20 MB
data/voices/<user_id>/ 声音复刻的临时样本 wav（10–20 秒、24kHz 单声道，约 0.5–1 MB） 用完即删，正常恒为空目录；每个账号只留一副音色的记录（在 SQLite 里，不占这份磁盘）

粗算（COMPRESS_TARGET_MB=50）：平均每人每次上传约吃掉 55–70 MB，USER_UPLOAD_LIMIT=5（每人保留 5 个视频），10 个人用满约 3 GB。 没开压缩时按上限算就是另一回事了：200 MB 上限 × 5 个 × 10 人 ≈ 10 GB 起步，所以这台机器上不要把 COMPRESS_TARGET_MB 填 0。

临时占地：压缩过程中会在 data/videos/ 里写两类临时文件 —— 一份 <原名片段>.compressing.mp4（压好的成品，大小 ≈ 目标体积）和若干 <原名片段>.compressing.pass0.log*（两遍编码的统计文件，几 MB 以内）。峰值占用 = 原文件 + 目标体积，所以 200 MB 的原片在最坏瞬间要 250 MB 空闲。正常结束和报错都会清掉临时文件；只有进程被 kill -9 才可能残留，看到 .compressing 开头的直接删（数据库里不会引用它们）。

7.2 关键事实：系统没有任何自动清理

视频与中间产物只在用户主动删除时才会消失。必须做磁盘监控，否则磁盘写满后的症状是：SQLite 报 database or disk is full，上传失败，且服务可能反复重启。

bash
# 每天看一次（或接你的云监控告警：磁盘使用率 > 80% 报警）
df -h /opt/speech-assist | tail -1
du -sh /opt/speech-assist/data/videos /opt/speech-assist/data/artifacts

# 找出最占地方的视频（文件名里带 user id 与上传时间戳）
ls -lS /opt/speech-assist/data/videos | head -20

7.3 三种扩容方案

  1. 控制台扩容系统盘（推荐，最省事）：ESSD 支持在线扩容 → 阿里云控制台"云盘扩容" → 服务器里 growpart /dev/vda 1 && resize2fs /dev/vda1（分区号按 lsblk 实际输出）
  2. 挂数据盘并把数据目录迁过去：把盘挂到 /data，然后在 unit 里改一行
    bash
       # /etc/systemd/system/speech-assist.service
   Environment=DATA_DIR=/data/speech-assist-data
   # 迁移：systemctl stop speech-assist
   #       mkdir -p /data/speech-assist-data && mv /opt/speech-assist/data/* /data/speech-assist-data/
   #       chown -R speech:speech /data/speech-assist-data
   #       systemctl daemon-reload && systemctl start speech-assist
  3. 降容量：在 /settings 把 COMPRESS_TARGET_MB 降到 30（新上传的才会压到这个体积，热生效）、MAX_VIDEO_MB 降到 100、USER_UPLOAD_LIMIT 降到 3。降压缩目标比降上传上限有用：上限只影响拒收，目标才是决定每个文件真正占多少磁盘的那个数

7.4 清理谁的数据

不要直接 rm 文件 —— 数据库里会留下指向已消失文件的记录。正确做法：让对应用户在页面上删除视频（走 /videos/{id}/delete，会同时删记录与文件），或在 /admin 里删用户。

只有确认是孤儿文件（数据库里没有对应记录）时，才手工清：

bash
sqlite3 /opt/speech-assist/data/speech.db 'select file_path from videos;' # 有记录的合法文件
# 比对 ls 结果，只删不在列表里的

sqlite3 若未安装：apt-get install -y sqlite3。日常不需要，备份脚本用的是 Python 标准库。

8. 升级与回滚

升级 = 重新打一个包，然后跑 update.sh。

powershell
# 本地
powershell -ExecutionPolicy Bypass -File deploy\package.ps1
scp dist\speech-assist-20260928.tar.gz root@<公网IP>:/root/
bash
# 服务器：参数可以给 tar.gz，也可以给已解压的目录
cd /opt/speech-assist
sudo bash deploy/update.sh /root/speech-assist-20260928.tar.gz

update.sh 的流程（顺序很重要）：

  1. deploy/backup.sh —— 升级前自动备份（数据库 + .env + 密钥 + 提示词/评分标准）
  2. rsync -a --delete 同步代码，同样保护 .env / api_key.txt / data/ / .venv / backups/。同步前先读旧 BUILD_INFO.json、同步后读新的，打印"代码指纹：old -> new"；新包没带指纹、指纹是 unknown、或新旧一致，都会显式警告（"没变"通常意味着传错包或忘了重新打包）
  3. pip install -r requirements.txt 补依赖变化
  4. 从已安装的 unit 里读回 --host/--port，重新渲染 systemd / nginx 配置，保证端口不漂移
  5. nginx -t 先校验再启用（失败自动回滚旧配置），systemctl restart speech-assist
  6. 轮询 /health 判定成功，并把返回的 version 与第 2 步的新指纹对账——对不上判失败。这一段是"假升级"的终结者：/health 一切正常但跑的还是旧代码的情况，从此会被脚本自己抓出来

服务中断时间约 3–8 秒（reload nginx 不中断，restart 应用会中断）。低峰期执行。

新增的配置键不会自动出现在老 .env 里：rsync 保护 .env 意味着升级后它仍是原来那份。缺的键走内置默认值（声音复刻这一对的新默认是 VOICE_CLONE_ENABLED=1 + TTS_VC_MODEL=qwen3-tts-vc-2026-01-22，也就是新功能默认开着，只想维持旧行为的要在升级后补 VOICE_CLONE_ENABLED=0；本次新增的 REVISE_TIMEOUT 缺省即 600 秒、TOPIC_MATCH_THRESHOLD 缺省即 0.6，都不必补），或者登录后进 /settings 拉到底保存一次 —— 页面必然提交全部 47 项，缺的键会被原样追加到 .env 末尾（保留注释、顺序与换行风格），这也是最省事的补齐办法。

回滚：备份里有数据库与配置，代码回滚 = 用旧包再跑一次 update.sh /root/speech-assist-<旧日期>.tar.gz。数据库回滚：

bash

cp -a /opt/speech-assist/backups/<时间戳>/.env /opt/speech-assist/.env
systemctl start speech-assist

10. 已知限制（提前告诉用户，比事后解释强）

限制 影响 能做什么
3 Mbps 出网（约 375 KB/s） 两人同时在线回看视频会明显卡顿；一人看勉强，多人看必卡 只能升带宽（阿里云按固定带宽计费，5 Mbps 约翻倍价格）；或让用户先看报告文字、需要时再单个回看；nginx 已配 proxy_buffering off，不浪费带宽在缓冲上
2 vCPU 共享型（无 SLA 抖动余量） 分析是 ffmpeg 抽帧 + 网络等待，CPU 峰值短但会互相抢 MAX_ANALYZERS=2 已与"两人同时"对齐，不要调大
自动压缩要占满 CPU 超过 COMPRESS_TARGET_MB 的视频，分析前要先跑两遍 x264 编码。折算耗时 ≈ 每分钟 1080p 素材 1~2 分钟（2 vCPU），即 3 分钟片子约 3~5 分钟、15 分钟约 15~20 分钟（来源见本节末）。这段时间该任务只占一个分析名额，别人的上传/看报告不受影响，但第二个人点分析会多等这么久 这是磁盘与带宽换来的必要代价（见 §7.1）。要更快只能：调大目标（压得少 → 传得快的问题仍在）、或换更大的机器（§12.5）。不要为了省 CPU 把目标填 0，那等于让 40 GB 系统盘直接面对 200 MB 的原片。可行性闸门会先替你拦一道：默认 COMPRESS_TIMEOUT=1800 下超过约 22 分钟的素材根本不会开压（"必超时"拦截，秒级失败），所以这段占 CPU 的时间有硬上界
内存 2 GiB 应用本身够用（实测 2 并发峰值 500–600 MB），但没有冗余 已建 2 G swap 作 OOM 保险；绝对不要把 ASR_ENGINE 改成 whisper
单进程 uvicorn 单进程 + FastAPI 线程池（WEB_THREADS=32），够撑住并发请求 想扩容的正确方式是换更强的机器，不是加 worker
HTTP 明文 口令与视频走公网明文 这是你选的方案。要收紧就上一张免费 DV 证书 + 域名（第 12.4 节）
评分标准文件名硬编码 评价标准.txt 必须在应用根目录，不能用环境变量指向别处 别改这个文件名
数据只在本地磁盘 实例被释放 = 数据全丢 第 9 节的异地备份
「示范朗读」按字符计费且必须在线 每点一次「合成朗读」就是一次真实的大模型调用；稿件按 TTS_CHUNK_CHARS（默认 1600 字）切块、逐块请求，演绎指令随每块重复发送并计入 characters，反复重合成会放大账单 不要就把 TTS_ENABLED 填 0（页面只留文字稿，不显示合成入口）；换音色 TTS_VOICE（默认 Neil，女声 Cherry）；要省钱就调小 TTS_MAX_CHUNKS。同理 REVISE_ENABLED=0 可整块关掉改稿建议。两键都是新增能力，填 0 即退回旧行为
「我的音色」声音复刻按次计费且必须在线 每建一次音色 = 一次 qwen-voice-enrollment 调用，记在 creations 里不吃 token；样本只取自学生勾选「就用这一段」的那条视频，抽完即删（磁盘上不成人声库），授权时间、样本出处、绑定模型三样都留痕。入口关掉 ≠ 数据删除：VOICE_CLONE_ENABLED=0 只锁页面与三个 POST，已授权的记录和已建好的音色一概保留，填回 1 立刻能用；撤回授权会连带删音色，删音色不会反过来清授权留痕。音色绑在 TTS_VC_MODEL 上，管理员改这个键等于让全站的旧音色集体判作废（见第 5 节的改配置表）。设计取舍见设计报告.md §15.6，实现口径见方案文档 §9

"每分钟 1080p 素材 1~2 分钟"这个折算系数的来源（别当成拍脑袋的数字）：在 32 逻辑核的开发机上，用 testsrc2 合成一段 60 秒 / 1920x1080 / 25fps 的片段（43.2 MB），设目标 20 MB 跑真实两遍编码，结果是 19.0 MB、耗时 5 秒、未降分辨率（保持 1080p 原生，视频码率 2656 kbps）。按核数线性折算到 2 vCPU 即 5 × 16 = 80 秒 / 每分钟素材。这个折算偏保守：x264 的多线程是次线性扩展（核数少时单核效率更高），而 testsrc2 是满屏噪点，比真人讲话的固定机位画面难压得多。手机竖屏 720p 的实际耗时通常只有上面数字的一半上下（像素少一半，而且多数会被阶梯降到低一档）。

403 且 URL 是 /health — 正常，nginx 故意只允许 127.0.0.1

上传时要等一两分钟才跳转，用户以为死机 journalctl -u speech-assist \| grep '\[上传\]' \| tail 先看这一行的接收段。生产机实测一行：[上传] heyun 36.1 MB｜接收 97.46s（ 0.4 MB/s） 转存 0.05s …｜… → /videos/…（自动分析）——接收占 99% 以上 = 3 Mbps 出网把传输时间摊给了用户（第 10 节），本项目自己的三段合计不到 0.1 s，不是故障，服务端也无从优化。想变快只能升带宽或调小 COMPRESS_TARGET_MB；只有"转存/入库/入队"占大头才需要继续查服务端。前端已改为点提交后原地显示上传进度（百分比 / 已传与总体积 / 实时速度 / 预计剩余 / 取消按钮，设计报告 §8.5），等待至少可见；若页面长期停在"正在建立连接…"，多半是这台机器到服务器的上行更慢，不是接口挂了。另注意 97 s 的接收已逼近 nginx proxy_read_timeout 300s，接近 100 MB 的文件有 504 风险，要么同步放大该值，要么压小体积
上传报"网络错误"、页面卡住 journalctl -u speech-assist -n 50 多半是 REQUEST_TIMEOUT 大于 nginx proxy_read_timeout（模板里已是 300s > 180s）。若你调大了超时，两边要一起调。REVISE_TIMEOUT=600 不在此列——修订生成是后台任务，HTTP 请求秒回、页面轮询拿进度，慢调用不占用任何一条 nginx 连接
报告分数是演示数据 /health 的 mode mock：api_key.txt 缺失/不可读（chown speech:speech + chmod 600）或 key 无效（key_is_valid 要求长度 ≥ 12）
分析失败，错误里带「ffmpeg 压缩失败」或「两遍编码后仍有 XX MB」 /health 的 ffmpeg、.env 的 COMPRESS_TARGET_MB 压缩是显式失败，原文件保留着，不会静默按超限体积继续跑。ffmpeg: false → apt-get install -y ffmpeg + 重启；ffmpeg 在但报"两遍编码后仍有"→ 目标压得太狠（比如要求把 1 小时 1080p 压进 20 MB），把 COMPRESS_TARGET_MB 调大或让用户重传短一点的片段。两种情况都可以在页面上直接点「重新分析」重试，不用搬文件
分析只失败了几秒，错误含「这个时长至少需要 X MB」或「必然被中断」 视频的实际时长、.env 的 COMPRESS_TARGET_MB / COMPRESS_TIMEOUT 这是可行性闸门在 ffmpeg 启动前的正常拦截（设计报告 §5.1.3），不是故障：长视频压不进 50 MB 或必超时，早失败比跑半小时被 kill 好。出路按错误提示来——让用户剪辑分段，或调大 COMPRESS_TARGET_MB / COMPRESS_TIMEOUT（网页即可改）。原文件保留。确认误拦可把 COMPRESS_FEASIBILITY 填 0 退回旧行为
大视频分析卡在「自动压缩到目标体积」很久 journalctl -u speech-assist -f、top 里 ffmpeg 的 CPU 正常现象：两遍编码要占满 CPU（见第 10 节）。进度条会一直动，每一遍各按 COMPRESS_TIMEOUT 计时，超一遍就报错并保留原文件。闸门已把"必超时"的长件提前拦掉，能走到这一步的理论上都在预算内
网页能开但分析一直"排队中" /health 的 concurrency.running 前面任务卡在网络请求上（REQUEST_TIMEOUT=180 最长 3 分钟）。确认出网可达 dashscope.aliyuncs.com：curl -sI https://dashscope.aliyuncs.com

登录成功但刷新又掉线 浏览器是否禁 Cookie SESSION_DAYS=7；若手工给 Cookie 加了 secure=True 而用 HTTP 访问会立刻失效 —— 保持现状（只有 httponly + samesite=lax）

11.1 忘了管理员口令（不影响普通用户）

口令是 PBKDF2-SHA256 哈希存在 users.password_hash 里的，没法"查看"，只能重置。用应用自己的虚拟环境直接改那一行（不要用 delete from users —— videos.user_id 是 ON DELETE CASCADE，会连带删掉该账号的视频与评价记录）：

bash
cd /opt/speech-assist

from app import db, security

with db.get_conn() as c:
    row = c.execute("select id, username from users where role='admin' order by id limit 1").fetchone()
    if row is None:
        print("没有管理员账号：改 .env 的 ADMIN_USERNAME/ADMIN_PASSWORD 后重启服务即可自动建号")
    else:
        c.execute("update users set password_hash=? where id=?", (security.hash_password(new_pw), row[0]))
        print("已重置管理员：", row[1])
PY

改 .env 里的 ADMIN_USERNAME 再重启会多出一个管理员账号（init_db 按用户名判断存在性），而不是改名。要改名请在 /settings 里改，那里走的是 sync_admin_login，会重命名第一个管理员。

12. 常见变更怎么做

12.1 换端口

bash
sudo bash deploy/install.sh --listen-port 8080    # 会重渲染 nginx 并 restart
# 别忘了：安全组放行 8080

12.2 不要 nginx

bash
sudo bash deploy/install.sh --no-nginx --listen-port 8080
# 此时 uvicorn 直接监听 0.0.0.0:8080，安全组放行 8080
# 代价：没有 gzip、没有安全响应头、/health 不对公网隔离、上传体积只受 MAX_VIDEO_MB 限制

12.3 把本地已有的数据搬上服务器

powershell
# 本地：先停本地服务，保证 sqlite 不处于写入状态
scp data\speech.db root@<公网IP>:/opt/speech-assist/data/
scp data\speech.db-wal root@<公网IP>:/opt/speech-assist/data/   # 如果存在
scp -r data\videos    root@<公网IP>:/opt/speech-assist/data/
scp -r data\artifacts root@<公网IP>:/opt/speech-assist/data/
bash
chown -R speech:speech /opt/speech-assist/data
systemctl restart speech-assist

搬过去之后老用户的口令仍然按本地哈希生效；SECRET_KEY 变了，所有人需要重新登录一次。 注意 .env 里的 MAX_VIDEO_MB 若比本地小，历史大文件仍可回看，只是不能再上传更大的。

12.4 将来要 HTTPS（本次不做，留个路径）

需要：一个已备案的域名（解析到这台机器的公网 IP）+ 一张证书（阿里云有免费 DV 证书，或用 certbot + Let's Encrypt）。 改动：/etc/nginx/conf.d/speech-assist.conf 里加 listen 443 ssl + 证书两行 + 80 跳转 443；安全组放行 443。 同时要把会话 Cookie 加上 secure（app/main.py:207 的 _set_session），否则 HTTPS 下白做。

12.5 换更大的机器

机器规格变化后需要同步调的参数：.env 里 MAX_ANALYZERS、MAX_LLM_REQUESTS、WEB_THREADS，以及 MAX_VIDEO_MB（带宽提升后再放宽）。改完 systemctl restart speech-assist，并重跑 install.sh 让 nginx 的 client_max_body_size 重新对齐。
