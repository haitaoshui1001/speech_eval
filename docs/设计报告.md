## 1. 设计目标与非目标

### 1.1 目标

1. 账号**由管理员统一开通**（后台单个录入或 Excel 批量导入），用户登录后上传演讲视频，一键触发分析，全过程可视化进度；站点**不开放自助注册**。
2. 系统完成 **语音转录 → 多模态判分 → 证据核验 → 反馈生成** 的完整链路，且严格按《评价标准》逐维度打分。
3. 输出**可复现、可审计**的分数：分数由确定性规则聚合，不依赖模型情绪；评语必须由大模型生成，但**不得反向修改分数**。
4. 同一用户多次上传可按维度对比，并识别**反复出现的同类问题**。
5. 管理员可见全站视频、评价、用量与统计，普通用户之间的数据严格隔离。
6. 无 API key 时也必须能跑通全流程（演示模式），便于验收与教学演示。
7. 对"眼神回避 / 不正视评委 / 表情不自然"这类主观判断，提供一层**可复现的客观测量做交叉核对**（正脸率、头部偏向、疑似低头），只作质控证据与人工复核指路，不进入加权求和（§5.1.2）。
8. `.env` 里的运行参数（运行模式、评审通道开关、抽帧密度、站点上限与安全项）都能在**管理员网页**上看懂、改对、改完立刻生效，不必登录服务器编辑文件（§13）。
9. 面向**至少 10 个用户同时操作**：把"网页请求 / 视频分析 / 千问在途请求"三层额度拆开独立可调，在设置页可改、`/health` 可查，避免一处堵死处处转圈（§14.4）。
10. 发给大模型的**提示词也是管理员可维护的配置**：19 块提示词在同一个设置页上可读、可改、可一键恢复内置默认，改动受占位符与输出结构校验保护，保存即对下一次分析生效（§13.8）。

### 1.2 非目标

- 不做多租户横向扩展、不做分布式任务调度、不做对象存储。
- 不做实时（流式）视频评测，只处理上传完成的文件。
- 不承诺分数与人类评委完全一致；本系统追求的是**同一输入产生稳定且可解释**的结果。
- 不做视线方向估计、表情单元（AU）识别或眨眼频率测量——关键帧是稀疏静态画面，且 Haar 级联测不出注视角；报告里出现这类结论时，它来自大模型的看图判断，而非测量值。

## 2. 技术选型与依赖

| 层 | 选择 | 理由 |
| --- | --- | --- |
| Web 框架 | FastAPI + Uvicorn | 表单/文件上传与类型校验自带；路由多为同步（FastAPI 自动丢进 anyio 线程池），只有 `/health` 必须 `async`——anyio 线程闸门只能在事件循环内读取（§14.4） |
| 视图 | Jinja2 服务端渲染 + 单个 `style.css` | 无 JS 框架、无构建步骤，页面可离线打开、可 Ctrl+P 打印 |
| 图形 | 服务端拼 SVG（雷达图、趋势图、Δ 条） | 避免引入图表库与 CDN；SVG 可选中、可打印 |
| 存储 | SQLite（标准库 `sqlite3`，WAL + 外键） | 单机零运维；外键级联删天然满足"删号即清数据" |
| 模型 | DashScope OpenAI 兼容端点，仅用 `requests` | 不引入 openai SDK，便于精确控制流式与 payload 字段 |
| 音视频 | 外部 `ffmpeg` / `ffprobe`（subprocess） | 抽音轨、抽帧、切块、取时长，成熟且无需 Python 编解码依赖 |
| 可选本地 ASR | `faster-whisper`（延迟 import） | 不装也不影响启动；仅 `ASR_ENGINE=whisper` 时才需要 |
| 可选客观测量 | `opencv-python-headless>=4.10,<5`（延迟 import，`app/face.py`） | 只做正脸率/偏向一类**可复现测量**，用于交叉核对与质控；不装、装成 5.x（Haar 级联移出主 wheel）、或 `USE_FACE_METRICS=0` 时整块降级，评分链路不受影响（§5.1.2） |
| 账号 Excel | `openpyxl`（读写都要，`app/accounts.py`） | 模板下载与批量导入共用一套解析；不引 pandas——体积大且本机 pandas 与 NumPy 2.x ABI 冲突 |

`requirements.txt` 声明 7 个核心包（fastapi、uvicorn[standard]、python-multipart、jinja2、python-dotenv、requests、openpyxl）+ 1 个可选的 opencv，刻意保持最小面。Excel 读写只用 `openpyxl`（§8.1），不引 pandas——本机 pandas 与 NumPy 2.x 存在 ABI 冲突，装了也 import 不了。

### 3.3 一次分析的时序

```
POST /videos（上传，流式写盘，超上限即删）
  └─ pipeline.enqueue(vid) → 状态 queued
       └─ 线程池 _worker → run_analysis(vid)
            ├─ 8%  analyzing  抽取音视频与关键帧   media.probe / extract_audio / extract_frames_timed
            ├─ 15% analyzing  逐帧朝向测量（可选）  face.measure()  → 只作质控证据，不进分数

            ├─ 84% analyzing  聚合分数与证据核验     analyze.aggregate()
            ├─ 92% analyzing  生成评语与总结         analyze.build_narrative()
            ├─ 99% analyzing  生成导师提问          analyze.build_questions() → db.add_usage（累加，非覆盖）

       异常 → status failed + error 文本（保留已消耗的 token）
```

### 4.2 设计要点

- **"双写 + 快照"**：`evaluations.payload` 保存完整报告（渲染只读它，保证历史报告可复现）；`dimension_scores` / `issues` 是同一份数据的可查询投影（对比、均值、复发检测）。重分析时先按 `video_id` 删除旧投影再插入，避免叠加。
- **状态机**：`uploaded → queued → transcribing → analyzing → done | failed`。
  进度百分比与 `stage` 文案由 `db.set_progress()` 单点写入，前端 2 秒轮询 `/videos/{id}/status`。
- **重启自愈**：进程被杀会使任务永远卡在 `analyzing`。启动钩子调用 `db.reset_stale_jobs()`，把所有进行态改为 `failed` 并给出"请重新点击分析"的中文原因，用户可一键重试。
- **列级迁移**：新增列没有引入迁移框架，只用 `PRAGMA table_info(<表>)` 比对 `_EXTRA_VIDEO_COLUMNS` / `_EXTRA_USER_COLUMNS`，缺列即 `ALTER TABLE ADD COLUMN`。老库直接升级，无需删库。
  > 代价：`evaluations`/`issues` 若未来加列，需要同样登记到 `_migrate()`。
- **上传配额是"计数列"而不是"查询统计"**：`users.upload_used` 在 `create_video()` 里 `+1`、在 `delete_video()` 里 `MAX(0, -1)`，因此**删掉一条视频就返还一次名额**——用户的直觉是"名额 = 我还能传几个"，不是"我历史上点过几次上传"。若改成 `COUNT(videos)`，一次失败分析、一次误传再删都会永久吃掉名额，且和"管理员重置已用次数"这个动作对不上。`upload_limit` 与 `frontal_ratio` 同理用 **NULL 表示"未单独设置、跟随全局"**，与显式填 `0`（禁止该账号上传）含义相反。
- **删除即清盘**：管理员删视频/删用户时，除数据库级联外还显式 `rmtree(data/artifacts/<id>)`，避免抽帧产物成为孤儿。
- **导师提问是"整组重建"的从属数据**：`qa_turns` 一行一题、作答与点评同行，外键挂 `videos`/`users` 并 `ON DELETE CASCADE`——`delete_video()` 只显式删 `issues`，其余子表都靠级联，所以新表漏写外键就会留下孤儿行，而 SQLite 复用 rowid 时旧作答还会串到新视频上。出题走 `save_questions()`：先 `DELETE` 再插，重出不累积、旧作答随之作废；`save_evaluation()`（重分析）同样清 `qa_turns`，因为题目是从属于某一份评价结果的。

## 5. 核心流程：转录与三通道评价

### 5.1 媒体预处理（`media.py`）

| 步骤 | 实现 | 约束 |
| --- | --- | --- |
| 探测 | `ffprobe -print_format json` | 取时长/分辨率；失败抛 `RuntimeError` → 视频进入 failed |
| 封面 | `video_thumbnail(at=min(1.5, duration/3))` | 避开第一帧黑屏 |
| 音轨 | `extract_audio(..., max_seconds=900)` | 16k 单声道 wav；**最长 15 分钟**，超出截断并在质控中提示 |
| 关键帧 | `extract_frames_timed()`（内部只有 `_uniform_frames` 一条路径） | 张数由 `frame_budget(duration)` 按 **每 `FRAME_INTERVAL=5` 秒一张**推导，**只封上限不抬下限**（`min(FRAME_COUNT_MAX, 100)`），写 `artifacts/<id>/frames/frame_NN.jpg` 并**回传每帧真实采样时刻** |

产物目录结构固定为 `data/artifacts/<video_id>/{cover.jpg, audio.wav, chunks/, frames/}`，Web 层只允许按白名单正则读取（见 §7.4）。

#### 5.1.1 关键帧张数：按时长自适应（每 5 秒一张，只封上限）

张数不再是常量。`frame_budget(duration)` 按"每 `FRAME_INTERVAL` 秒一张"推导，**只做上限封顶**，不做下限抬高：

```python
if duration <= 0:  return max(1, min(settings.frame_count, _FRAME_HARD_CAP))  # 探测失败退回 FRAME_COUNT=12
step = max(1, settings.frame_interval)                                          # 5
hi   = max(1, min(settings.frame_count_max, _FRAME_HARD_CAP))                   # 100
return max(1, min(int(round(duration / step)), hi))                             # 1 … 100
```

实测曲线（`tests/selfcheck.py` §8 钉住）：**0s→12、1s→1、8s→2、42s→8、145s→29、3600s→100、86400s→100**。

**下限夹进取掉了，这是本轮最重要的口径变更。** 上一版把张数夹进 `[FRAME_COUNT_MIN=6, FRAME_COUNT_MAX=36]`，结果是 8 秒的视频被硬摊成 6 帧（每 1.3 秒一张）、15 分钟的又被压在 36 帧（每 25 秒一张）——两头都不等距。等距是这条链路的硬需求（视觉通道一次请求要看完整帧序列才能判"随时间的变化"，采样忽密忽疏会让"每帧代表多久"这个隐含口径失效），所以改成**短视频就少采、长视频多采**，`FRAME_COUNT_MIN` 已从配置项、设置页与校验逻辑里整体删除。同理，上限从 36 提到 **100**（千问视觉单次请求图片数上限），长视频的覆盖密度不再被人为截断。

抽帧本身是**纯均匀采样**，且**每帧带回真实采样时刻**（`FrameSet(paths, stamps)`）：

1. **等距铺满是唯一策略**：`step = duration / count`，采样点取每段中点 `step*(i+0.5)`，逐点 `-ss` seek 单帧导出。逐点 seek 的时刻就是请求的 target，天然精确，不需要事后推测。
2. **场景切换补插已整体删除**：`_scene_frames()`、`_largest_gap()` 与 `SCENE_THRESHOLD` 配置项一并移除。它们会把采样点从等距格子上拽偏——而"每帧代表 `step` 秒"正是上面整套推理的前提。旧版为场景帧做的四处 ffmpeg 兼容处理（`format=yuvj420p`、`-fps_mode vfr` 降级阶梯、`isnan(prev_selected_t)` 放行首帧、从 `showinfo` 解析 `pts_time`）也随之消失，抽帧命令只剩"seek + 单帧 + 缩放"这一种形态。
3. **缺点不回填**：个别采样点抽取失败就直接少一帧，剩余帧按真实时刻排序后**重新连续命名** `frame_NN.jpg`。宁可少一张证据，也不能让"第 i 帧对应第 t 秒"错位。
4. **全失败兜底**：一帧都没有时退化为在 `duration/2` 处抽单帧，报告仍能出。

`tests/selfcheck.py` §7 用合成硬切探针视频（白/黑/红三段 + 测试图）把"均匀"这个性质钉死，而不是只数张数：

- **相邻帧间隔恒定**：`max(deltas) - min(deltas) <= 0.05s`——旧版有场景补插时这条必然失败，它守的就是"不许再把格子拽偏"；
- **采样点落在格子中点**：首帧必须约等于 `step/2`，防止实现漂回"从 0 秒开始抽"（抽到片头黑屏）；
- **硬切夹具不被误删**：抽满预算张数，帧文件按 `frame_00 … frame_NN` 连续编号；
- **时间戳与帧一一对应且单调递增**。

（夹具仍刻意选白/黑/红三段：历史上这套颜色是为"场景分数按亮度直方图计算"选的，现在保留是为了万一将来重新引入内容感知采样时，夹具不会因为等亮切换而误报故障。）

缩放是 `scale=w='min(iw,FRAME_WIDTH)':h=-2`（默认 640）——`min(iw,...)` 表示**只缩不放**，竖屏素材原始宽度常小于 640，放大只会白涨视觉 token 换不来细节。编码 `-q:v 3`，体积门槛 **512 字节**：纯色背景或白底 PPT 压完可能不足 1KB，门槛定到 1KB 会把合法帧当失败丢掉。

取值理由按重要性排序：

| 理由 | 说明 |
| --- | --- |
| 维度要判"随时间的变化" | 「态势语与舞台表现」「结构与时间控制」需要覆盖开场/中段/收尾才能判断"是否走动""是否全程低头念稿""结尾是否仓促"。1–2 帧只能判**状态**，不能判**变化**。 |
| 覆盖密度要随时长走 | 2 分钟与 15 分钟的演讲用同一张数，长视频会退化成"每 75 秒一张"的抽样噪声。**等间隔 + 每 5 秒一张**同时满足两件事：密度随时长走，且任意两帧之间的时间跨度恒定。短视频不再被抬底凑数（10 秒就老实抽 2 帧），长视频不再被上限截断（可到 100 帧）。 |
| token 与时延线性可控 | `qwen.IMAGE_TOKENS = 1000`，帧数即输入 token 的斜率（8 帧 ≈ 0.8 万、29 帧 ≈ 2.9 万、100 帧 ≈ 10 万）；且 `client.vision()` 把全部帧放在**同一次请求**里（须让模型看到前后对比才能判变化），`FRAME_COUNT_MAX` 就是这个请求体积的保险丝。 |
| 证据锚点数 == 帧数 | 视觉通道强制模型以 `frame@mm:ss` 形式给证据（`schema_hint` + `common_rules`），聚合层用 `_frame_ok()` 校验。张数与时长挂钩后，锚点密度稳定，不会出现"15 分钟只有 12 个锚点、模型只能靠编"的窘境。 |

两条必须知道的边界：

- **硬上限 100**：千问视觉单次请求图片数上限就是 100，`_FRAME_HARD_CAP = 100` 与 `FRAME_COUNT_MAX` 默认值同值，`frame_budget()` 与 `extract_frames_timed()` 两处都再夹一道，防止设置页填入超界值后请求被服务商整批拒收。资源白名单相应放宽为 `ASSET_RE = ^(?:cover\.jpg|audio\.wav|frames/frame_\d{1,3}\.jpg)$`（旧版只认两位序号，100 张起会被报告页静默过滤、被资源路由拒绝）。帧文件名仍是 `frame_{i:02d}.jpg`——`02d` 在三位数时自然变宽，`{1,3}` 正是为这个上界预留。
- **时间戳是真实值**：提示词里的 `frame@` 序列直接用 `FrameSet.stamps`，`_frame_ok(quote, duration, stamps)` 在**有帧表时**要求 `min(abs(t - s)) <= 2.0`，即时间点必须落在某张确实抽出来的画面附近 ±2s。只卡时长上界的话，模型编一个"视频里有、但没被抽到"的时刻照样通过，证据核验形同虚设——这一条补上了旧版视觉证据比文本证据（`verify_quote` 要求实词重叠 ≥ 0.55）弱一档的缺口。

#### 5.1.2 微表情的客观测量层（`face.py`）

需求侧要判"眼睛乱瞟、不正视评委、表情不自然"。落地方案是与需求方确认过的**路线 B：轻量先行**，四条硬约束：

| 约束 | 实现 |
| --- | --- |
| 不新增大模型请求 | 复用同一批关键帧，在本地跑 OpenCV Haar 级联；视觉通道仍是**一次**请求，只是提示词里多了逐帧判读指令与一段客观核查块。 |
| 不参与加权求和 | 指标只作**质控证据**，分数仍由模型判分 + 确定性聚合产出，与历史报告口径可比。 |
| 能力边界诚实 | Haar 只能可靠区分「正脸 / 侧脸 / 无脸」和「脸在画面里的位置」。真实视线方向做不出来（双眼级联在同一批真实帧上极少同时命中），所以只报"头部朝向偏离""疑似低头"，**不假装能测注视角**；`evidence_block()` 里明写"该测量不含视线方向"。 |
| 缺依赖整块降级 | `opencv-python-headless` 是可选包，延迟 import；`USE_FACE_METRICS=0`、未安装、或装到 **5.x**（Haar 级联已移出主 wheel，`cv2.CascadeClassifier` 不存在）时 `available()` 返回 False 并给出 `unavailable_reason()`，评分链路零影响。requirements 里因此锁了 `<5`。 |

门控链（`measure()`）是这层的重点——**宁可不说，不可说错**：

1. `scanned < 3` → 不判断（"有效采样帧过少，不足以判断朝向习惯"）；
2. `face_rate < FACE_MIN_DETECT`（默认 0.5）→ **一个朝向指标都不输出**。低质/远景素材的正脸检出率可以低到两成，把"拍不清"当成"不看镜头"是直接扣分级别的误判；
3. `eye_reliability < 0.5` → 不给 `down_ratio`，只在 `notes` 留一句"眼睛级联可靠度仅 X%，未输出低头率"（合成样例实测 0%，真实素材约 43%，两种情况都不硬凑指标）；
4. `frontal_ratio < 0.35` → 追加核实提示"正脸率偏低：请核实是否长期侧对镜头/评委，而非镜头本身拍不清"。

降级时的文案同样受约束：`headline()` 返回理由而非数字，`evidence_block()` 输出"眼神与表情的判断只能依据画面本身，**不要引用任何未经测量的数字**"。`videos.frontal_ratio` 在门控未通过时**留 NULL 而不是 0**——NULL 是"没测准"，0 是"全程没正脸"，两者含义相反。

与模型判分的交叉核对放在聚合层（`_face_conflicts()`），**双向**且都以"分数保持不调整"结尾：

- 模型按眼神/表情扣分至 <70%，而本地正脸率 ≥80% → 提示人工回看那些时间点；
- 该项给到 ≥90%，而本地正脸率 <35% → 提示疑似漏判回避对视。

配套还有提示词侧的 `micro_rules` 块（原 `MICRO_EXPRESSION_RULES`，现已挪进 §13.8 的可编辑清单，5 条编号要求）：眼神与表情分别判、每帧给 `frame@时间点` 证据、不许合并成一句"台风欠佳"、**稀疏静态帧看不出眨眼频率就别扣分**（把不确定写进 `notes` 并调低 `confidence`）、与客观测量冲突时保留判断但必须写明理由而不许改分。


### 5.2 语音转录：本地还是云端？（`transcribe.py`）

**答案由配置决定，两条路都实现了：**

| `ASR_ENGINE` | 实际执行 | 模型标识 | 特点 |
| --- | --- | --- | --- |
| `qwen`（默认，当前 `.env` 即此值） | **云端**千问语音识别 | `qwen3-asr-flash`（不可用时降级 `qwen-omni-turbo-latest`） | 无需下载模型、CPU 机器即可；音频需上传，按 `_split_wav(chunk=175.0)` 切成约 3 分钟一段逐段提交 |
| `whisper` | **本地** faster-whisper | `faster-whisper:<WHISPER_MODEL_SIZE>`（默认 `small`，`device="cpu"`, `compute_type="int8"`） | 完全离线、零 token 成本；首次运行需模型权重，CPU 上速度较慢；异常或空结果时**自动回落云端**并在质控记录里说明 |

引擎判定发生在 `transcribe()` 内一行分支：`if settings.asr_engine == "whisper":`。切引擎**只改 `.env`，无需改代码或重建库**。

一个必须写明的差别：本地路径在 `_whisper_asr()` 里显式传了 `language="en"`（并开启 `vad_filter`、`beam_size=4`），即**本地引擎按英语演讲调优**；中文演讲请保持 `ASR_ENGINE=qwen`，千问 ASR 对中英文混合口语的识别明显更稳。这也解释了为什么默认值是 `qwen` 而不是"本地优先"。

当前状态可在三处自查，无需读源码：

- `GET /health` → `asr_engine`（`qwen`/`whisper`）、`asr_engine_label`（"云端 qwen3-asr-flash" / "本地 faster-whisper"）、`whisper_model_size`、`models.asr`
- `/guide`「转录与评审」区块（面向用户的中文说明）
- 首页 ledger「转录方式」格（只显示"本地引擎 / 云端引擎"，不显示模型名；`videos.engine` 仍在库里记实际生效值）

**可信度闸门 `credibility(text, duration)`**：ASR 在纯音乐/静音上会产出幻觉（例如把测试音转成 `"100.0"`）。三条规则任一命中即判 `credible=False`：

1. 有效词数 < 8；
2. 平均词长 < 1.8（几乎不含实义词，疑似纯音乐）；
3. 时长 ≥ 20s 且词密度 < 0.4 词/秒（明显低于正常语速）。

命中后**不会把报告清零**，而是：文本通道各维度置信度乘 0.5（下限 `_MIN_CONF=0.25`），并在质控里写明"结论仅供参考"。这是对"模型失误不应静默毁掉整份评价"的显式防御。

### 5.3 通道归属：谁给哪个维度打分（`analyze.channel_weights`）

不是"三个模型平均分"，而是**按维度语义分配权重**：

| 命中线索 | 权重分配 | 例子 |
| --- | --- | --- |
| `VISION_HINT`（态势/舞台/肢体/眼神/手势/着装…） | `{vision: 1.0}` 或含 vision 的组合 | 态势语与舞台表现 |
| `AUDIO_HINT`（发音/语调/连读/重音/节奏/停顿…） | `{audio: 0.6, text: 0.4}` | 发音与语调 |
| 其余 / `TEXT_ONLY_HINT` | `{text: 1.0}` | 语言准确性、内容与思想、主题契合度 |

- 通道集合是**动态**的：若标准里没有任何维度需要画面，就不会抽帧、也不会调用视觉模型（省 token，见 §9）。
- 越界判分会被丢弃并记账：某通道给不属于它的维度打了分 → `qc` 追加"通道 X 越界判分，已忽略"。
- 该映射同时驱动 `/guide` 的「谁给哪个维度打分」表，做到**代码与说明书同源**。

### 5.4 确定性聚合（`analyze.aggregate`）

对每个维度执行固定流水线，全程无随机、无模型参与：

1. **置信加权融合**：`score = Σ(wᵢ·cᵢ·sᵢ) / Σ(wᵢ·cᵢ)`，`cᵢ` 钳制在 `[0.25, 1.0]`；维度置信度取参与通道的最大值。
2. **分歧降信**：多通道分差 > 满分 × 25% → 置信度 −0.15 并写质控。
3. **时长硬核查**：`check_timing()` 从 `requirements` 正则解析"2-3 minutes / 约90秒 / 01:30-02:30"等区间；若明显不达标，含"时间/timing"的维度得分收缩到满分的 60%。这是**唯一由代码强制改分**的客观规则（微表情指标刻意排除在外，见第 5 条）。
4. **证据核验**：
   - 文本类引语 → `verify_quote()`：子串命中，或去停用词后**实词重叠率 ≥ 0.55**；
   - 画面类证据 → 必须是 `frame@mm:ss`，且**有帧表时**该时刻要落在某张真实抽到的画面附近 ±2s（`_frame_ok(quote, duration, stamps)`）；
   - 未命中 → 标记 `evidence_ok=False`，置信度按每条 −0.1（最多 −0.3）。
5. **微表情交叉核对（只留痕、不改分）**：`_face_conflicts()` 双向比对——模型按眼神/表情扣分至 <70% 而本地正脸率 ≥80%，或该项给到 ≥90% 而正脸率 <35%，各写一条质控并显式以"分数保持不调整"收尾（§5.1.2）。
6. **无证据不下高分**：没有任何已核验证据、却得到 > 88% 满分 → 强制收缩到 85%（四舍五入到 0.5 分）。
7. **未评维度重标定**：某维度所有通道都不可信 → 标 `not_applicable`，其满分权重按比例分摊给其余维度（`raw_total / judged_max × rubric.total`），保证总分仍是 100 分制，同时质控写明折算过程。
8. **等级**：`band_of(pct)` → A ≥ 90 / B ≥ 80 / C ≥ 70 / D ≥ 60 / E。
9. **总分置信度**：按维度满分加权的平均置信度。

产物 `Aggregated(dimensions, total, max_total, band, confidence, qc, pct)`。

### 5.5 叙述层与"分数不可变"

分数确定后才调用 `build_narrative()`：提示词**只允许引用已确定的分项得分与已核验证据**，产出优点、缺点、可执行改进建议、总结与"下一步只练一件事"。

- 模型不可用/输出不合法 → `fallback_narrative()` 用维度数据拼出结构化中文，报告照常生成。
- 建议清洗 `_clean_suggestions()` 保证每条建议挂到真实维度上。
- 设计立场：**大模型负责解释，代码负责裁决**。任何"评语里说扣 5 分但分数没变"的不一致在结构上不可能发生。

### 5.6 报告快照结构

`build_report()` 返回（存入 `evaluations.payload`，pipeline 事后附加 `usage`）：

```
rubric_version, total, max_total, band, pct, confidence,
dimensions:[{key,name,name_en,index,max_score,score,ratio,band,confidence,
             strengths[],issues[{desc,quote,channel,evidence_ok,signature}],
             notes[],checkpoints[],not_applicable}],
advantages[], disadvantages[], suggestions[{text,dim_key,dim_name}], summary, next_focus,
timing{ok,note,duration,expected}, channels[{channel,model,confidence}],
evidence[], frames[], stamps[], face{available,scanned,face_rate,frontal_ratio,
nonfrontal_ratio,down_ratio,yaw_bias,head_spread,eye_reliability,headline,notes,frames[]},
qc[], provenance{asr_engine,judge_models,model}, usage{...}
```

`stamps[]` 与 `frames[]` 一一对应（真实采样时刻，`_frame_ok()` 与胶片带都靠它）；`face` 为 `FaceMetrics.to_dict()`，门控未通过时各比率为 `null` 且只带 `reason`。

### 5.7 评价之后：导师提问与作答点评

- **触发点**：`pipeline.run_analysis()` 在 `save_evaluation()` 之后、`set_progress(done)` 之前追加一步（进度 99，文案"生成导师提问"）。整步包在 `try/except` 里——出题失败最多是"这份稿子没有思考题"，绝不能把已经算完的评价报告判成 `failed`。
- **喂什么**：`analyze.build_questions()` 沿用 `build_narrative()` 的组装方式，把「演讲主题 + 老师要求 + 已定评价结果 + 讲稿节选」送进一次请求。评价结果**先剔除 `frames`/`stamps`/`face`/`transcript_excerpt`**——这些对"该问什么"没有信息量，却会白白吃掉上千 token。
- **模型只给建议，条数由代码保证**：空题会被丢掉，凑不满 3 条、JSON 解析失败或请求异常 → **整批**改用 `fallback_questions()`（从"改进建议 + 得分率最低的两个维度"生成，永远恰好 3 条）。不让真题与兜底题混排，否则一份卷子上会出现"两题贴稿、一题通用"的割裂感。
- **点评一次送评**：`review_answers()` 把三题「问题 / 学生作答」拼成一段文本，一次请求换回三条点评（省两次网络往返）；条数对不上或异常 → 三条整体换成 `QA_ANSWER_FALLBACK`，而**学生作答照常落库**——点评可以重出，答案不能丢。
- **演示模式**：`settings.real_mode` 为假时出题与点评都走本地兜底，绝不联网（见 §11）。
- **页面交互**：报告页最后一张「导师提问」卡片，题目下方就是作答框；尚未出题时显示"生成导师提问"按钮（补生成与自动出共用同一套代码）。提交后逐题在原位显示点评，跳转用 `?msg=` + `#qa` 锚点，保证刷新后仍停在提问区；三题任一为空即退回，不做半保存。
- **可调提示词**：出题/点评的 5 块挂在 §13.8 的第二张声明表里，`qa_system` 是两次请求共用的 system 角色——它同时管住"题只出自这篇稿子"和"点评只两三句话"。
- **额度同样入账**：流水线内自动出题与两条路由（补生成、提交作答）都用 `db.add_usage()` 做**累加**记账（§9.2）。这里绝不能用 `_flush_usage()`，否则会把分析阶段已记的 token 整段抹掉；记账放在 `finally` 里，请求失败也要入账——钱已经花出去了，账面装作没花是最坏的结局。

## 6. 多次上传的对比与复发问题

- `db.history_for_user()` 取最近若干次的 `evaluations`，`db.dims_for_video()` 取维度行 → `main.build_radar()` 叠加多次轮廓，`build_trend()` 画总分折线，`build_deltas()` 生成逐项 Δ。
- **眼神接触率第二折线**：`build_trend()` 在总分线之外叠一条虚线（`#1f5f8b` / `stroke-dasharray`），数据源是 `videos.frontal_ratio`，与总分**共用归一化纵轴**（各按自己的满分取比例），图例明写"本地逐帧测量，仅供质控参考，不计入分数"。`NULL`（未测/门控未通过）画成**断点而不是补 0**——否则趋势线上会出现一段假的"眼神突然变差"；也因此当中间有断点时，虚线会跨过空档直连，读数时要结合表格。
- 维度对齐按 `dim_key`（不是名称），标准改名后仍能对上；维度不同时只比较交集并提示。
- **复发问题**：`_signature(dim_key, desc)` = `dim_key : sha1(去标点小写前60字符)[:10]`，每次分析写入 `issues`。`recurring_issues()` 按 `signature` 分组，`HAVING n > 1` 即为"至少两次出现的同一问题"，附最近一次出现的视频，用于报告页"上次也提到过"和后台趋势提醒。
- 分析时把上次报告的最弱维度注入提示（`_history_note()`），使建议具有延续性。

### 7.2 会话

- 无状态签名 Cookie `sid`：`base64url("uid.role.exp.hmac")`，HMAC-SHA256（截 32 位十六进制）+ `hmac.compare_digest`，有效期 `SESSION_DAYS=7`。
- **角色只认数据库**：即使伪造出签名有效的 `role=admin` 载荷，路由仍以 `users.role` 为准（冒烟用例"签名有效但角色伪装无效"断言 403）。
- 口令 `pbkdf2_sha256`，180,000 次迭代，16 字节随机盐，格式 `algo$iters$salt$digest`。

### 7.3 越权与输入

- 统一入口 `owned_video()` / 管理员判定，跨用户访问一律 403（未登录 303 跳登录），避免"资源存在性"泄露成 200/404 差异。
- 上传：扩展名白名单（mp4/mov/m4v/webm/mkv/avi/mpg/mpeg/wmv/3gp）、逐 MB 累计校验 `MAX_VIDEO_MB=500`（超限即删半成品）、文件名 `re.sub(r"[^\w.\-]+","_")` 且截 60 字符、落盘名带 `uid-时间戳` 防覆盖。
- 所有页面文本经 Jinja2 autoescape；无 `|safe` 用于用户输入。

### 7.4 静态资源与播放

- `ASSET_RE = ^(?:cover\.jpg|audio\.wav|frames/frame_\d{1,3}\.jpg)$` —— **完全白名单**，路径穿越（`..%2f..%2fapp%2fmain.py`）必然被拒。序号放 1–3 位是为 `_FRAME_HARD_CAP=100` 预留余量（§5.1.1）。
- `play` 手工解析 `Range: bytes=a-b`：返回 206 + `Content-Range`，越界 416，无 Range 返回 200 全量，浏览器可拖动进度条。
- `Content-Disposition: inline` 且仅从 `settings.artifact_dir / str(video_id)` 拼接，不信任请求参数中的目录。

## 8. 管理员视图

`admin_stats()` 给出用户数、视频数、全站平均分与**按维度平均分**（`dimension_scores` 直接聚合，不解析 JSON）。后台页含：

1. 概览卡片（含"用量统计"面板：全站 token、均次消耗）；
2. 全部视频表（用户、标题、总分、等级、状态、用量、时间）；
3. **维度均分**（全站最弱维度一目了然）：`admin_dim_stats(topic)` 一次返回"按维度摊开"与"按人摊开"两张表，顶部下拉框按**主题**筛选（选项由 `video_topics()` 从实际数据里长出来，未填主题的归入「未填主题」桶，每个选项带条数）。加这个筛选是因为维度均分原本是全站平均——一个班同时交"自我介绍"和"命题演讲"时，两种主题混在一起的平均分没有任何可执行结论；筛完之后的"某人 × 某主题"才是能拿去反馈的口径；
4. **用量明细**：分阶段、分用户两视角 + 最近消耗（分模型的原始数据仍存库，只是不在界面上出现模型名）；
5. **账号开通**面板：逐个录入 + Excel 批量导入两条路（§8.1）；
6. 已开通账号表（视频数、平均分、token、开通日期、**重置口令**、**上传次数**（§8.2）、删号入口；`admin_stats().users` 只数 `role='user'`，不含管理员自己）。

管理员查看他人报告时，页面顶部标注"用户 <name> 的视频"，删除/重试入口对管理员同样开放。管理员**不再看到**「我的演讲」与「历次对比」两个入口（导航栏按 `role` 分支），并且直接访问 `/dashboard`、`/compare` 会被 303 回 `/admin`：管理员自己通常没有视频，那两个页面对他是一片空白，反而把真正该看的后台藏在了第二跳。

### 8.1 账号开通：两条路，一套校验

自助注册关闭后，账号只能从后台产生。`app/accounts.py` 是这条链路唯一的校验源（纯函数，不碰库也不碰文件），两条路共用它，因此**单个录入与批量导入的判定口径必然一致**：

| 环节 | 单个录入 | Excel 批量导入 |
| --- | --- | --- |
| 入口 | `POST /admin/users/create` | `GET /admin/users/template` → Excel 填写 → `POST /admin/users/import` |
| 校验 | `valid_username` + `password_ok` | `plan_users()` 逐行判定，额外管表头、示例行、文件内重名 |
| 建号 | `db.create_user()` | 先整表判定完，再对 `ready` 行逐个 `db.create_user()` |
| 回执 | 绿条"已开通账号 X"；出错回表单并回填已填内容 | "新建 N 个账号 / 退回 M 行（带行号原因）/ 跳过示例与表头 K 行" |

`plan_users()` 的判定顺序（已写进测试，逐条断言）：**首行像表头就丢弃** → **`#` 开头的用户名按示例跳过** → **中途再现的表头也跳过** → **三列全空直接忽略、不进任何统计** → **缺项 / 非法 / 重名退回** → 其余判为可导入。重名分两种：库里已有（`该账号已存在，未做任何改动`）与文件内更早的行（`与模板第 N 行重名`），都带行号退回。

三条防呆细节：

- **数字单元格去 `.0`**：学号常被 Excel 存成数值，`cell_text()` 把 `20250101.0` 还原成 `20250101`，否则管理员会开通一个用户登不上去的账号。
- **模板原样上传是安全的**：模板里两行示例用户名以 `#` 开头，导入时计入"跳过"，不会误建 `#zhang01`；下载后直接传回去，账号数不变。
- **导入只新增，不改不删**：重名行退回而不是覆盖口令，避免一份旧名册刷掉已有账号；退回行**不留半截账号**（整表判定通过后才写库）。

口令策略与自助注册时代一致：`pbkdf2_sha256` + 180,000 次迭代 + 16 字节随机盐。导入与重置之后**任何页面都不再回显明文**，模板「填写说明」里同步提醒"Excel 用完请删除，不要转发明文口令"。重置口令只替换哈希，用户名、视频、评价与抽帧产物都不动。

### 8.2 上传次数配额：一个计数列，三档覆盖

自助注册关闭后，账号是管理员批量开出来的，"每人能交几个视频"就成了必须能圈住的口子——不限次的话，一个账号可以被拿去刷几十条真实模型调用，费用全部记在站点头上。默认每人 **5 次**（`USER_UPLOAD_LIMIT`，见 §14.2）。

口径设计上有三个决定：

| 决定 | 实现 | 为什么 |
| --- | --- | --- |
| 用**计数列**而不是 `COUNT(videos)` | `users.upload_used`：`create_video()` 里 `+1`，`delete_video()` 里 `MAX(0, upload_used - 1)` | 配额要管的是"上传动作的次数"，不是"当前留存的视频数"。用户删掉一条想重传，必须能拿回名额；用 `COUNT` 表达不了这个语义，而且每次上传都要全表扫一遍 |
| 额度检查**在落盘之前** | `POST /videos` 先 `db.upload_quota()`，`remaining == 0` 直接回表单提示，不写一个字节的视频文件 | 500 MB 的失败上传既浪费磁盘也浪费用户时间；同时避免"文件已落盘但库里没行"的孤儿产物 |
| 账号级覆盖 + 全局默认两层 | `upload_limit` 列：`NULL` = 跟随 `USER_UPLOAD_LIMIT`，填数字 = 只作用于该账号，填 `0` = 停止该账号上传 | 管理员要么逐个改默认（改不动），要么只有"全局/无限"两档（太粗）。保留 `NULL` 这个第三态，才能在全局默认从 5 调到 8 时让**没有特殊安排**的账号自动跟上 |

管理员不占用额度：`upload_quota()` 里 `role == 'admin'` 直接返回 `limit=None / remaining=None`，界面显示"不限次数"。

后台每个账号一行「上传次数」折叠面板，三个按钮共用一张表单、靠 `action` 区分意图（`save` 按输入框写 / `reset` 已用清零、上限不动 / `default` 取消单独上限回到跟随全局）：

- **"清零已用"是日常主路径**——用户说"我再交一版"，管理员点一下就放行，不必去理解上限那一栏；
- `limit` 输入框**留空表示不改这一列**（和 §13.3"回填值 ≠ 生效值"同一条哲学：不要把没动的东西写回去），填 `0` 才是明确的封禁；
- 上限框是 `type=number`，人不可能在里面打出 `"default"` 这个词，所以"恢复默认"只能由按钮的 `action` 表达，而不是靠一个魔法字符串。

提示文案区分两种耗尽情形，避免用户去猜：`该账号已被管理员停止上传`（`limit == 0`）与 `上传次数已用完（3/5）`。普通用户在 `/dashboard` 顶部就能看到"已用 X / 共 Y、剩余 Z"，不用等到上传失败才知道。

## 9. 模型用量（token）统计设计

### 9.1 采集（`qwen.py`）

- 每次真实调用结束后 `self._track(payload, comp)` 记一条：`{stage, model, prompt, completion, total, estimated}`。
- `stage` 由 `client.mark("转录 ASR")` / `mark("文本通道")` 等业务标签决定，因此统计天然带"钱花在哪个环节"的维度。
- **优先信任响应 usage**（兼容 `prompt_tokens/input_tokens`、`completion_tokens/output_tokens`、`total_tokens`）。
- 流式或部分模型（omni 系列）不回 usage → 走估算并打 `estimated=True`：
  - 中日韩字符与全角标点：1 字 = 1 token；其余文本：4 字符 = 1 token；
  - 图像/关键帧：每张固定 1000 token；
  - base64 音频：每 900 字符 ≈ 1 token（16k 单声道 wav 约 47 token/秒）。

`usage_summary()` 汇总为 `{calls, prompt, completion, total, estimated_calls, by_stage[], by_model[]}`，按 total 倒序。

### 9.2 持久化（`pipeline._flush_usage`）

**分阶段刷库**而非结束时一次性写：转录完 flush 一次、每个通道完成再 flush 一次。因此分析中途失败（网络断、额度尽、模型不可用）时，**已消耗的 token 仍然留在库里**，不会出现"花了钱但账面上是 0"。写库异常被吞并只打印堆栈——统计失败绝不能拖垮评价主流程。

落到 `videos` 的 5 个字段（4 列 + `token_detail` JSON 明细）。

**`_flush_usage` 是覆盖写**，因为它汇总的是贯穿整条流水线的那个 `client` 的全部记录，每次刷库都写入"到目前为止的总量"。这也意味着它只能用于分析阶段：一旦分析结束后另起 `client` 调模型（学生点「生成导师提问」、提交作答），拿它刷库会把分析统计整段抹掉。

因此第二条写库路径是 `db.add_usage(video_id, usage)`——**读-改-写做增量合并**：读出行上已有的 4 个计数与 `token_detail`，把新用量按 `by_stage` / `by_model` 的 `name` 逐桶相加，`estimated_calls` 也累加，再整体写回；`calls` 为 0 时直接返回 `{}`，连 UPDATE 都不发（演示模式因此完全不受影响）。

配套细节：分析末尾最后一次 `_flush_usage` 之后立即 `client.reset_usage()`，出题阶段前补 `client.mark("导师提问")`，这样流水线内自动出题的 token 走 `add_usage` 累加，且不会误挂到"评语生成"阶段桶里；`qa_generate` / `qa_answer` 两条路由同样在 `finally` 里累加——**模型调用失败也要记账**，钱已经花出去了。

由于报告页取的是 `evaluations.payload` 里的 `report["usage"]` 快照，它始终是"本次分析"口径；`/dashboard` 与 `/admin` 取 `videos` 行，是含提问与点评的累计口径。两者不一致是刻意区分，不是数据错乱。

### 9.3 聚合（`db.token_usage`）

`token_usage(user_id=None, per_video=0)` 不依赖 SQLite JSON 扩展，在 Python 侧对 `token_detail` 做二次聚合，输出：

```
{analyzed, calls, prompt, completion, total, estimated_calls,
 by_stage[], by_model[], by_user[], videos[], avg_per_video}
```

- `by_user` 的名字形如 `昵称（username）`，后台直接展示；
- `videos` 为"最近消耗"明细（带 `estimated` 标记），按 `per_video` 限长；
- `total_tokens` 与 `api_calls` 全 0 的行直接跳过 → 演示模式与历史数据不会污染统计。

### 9.4 展示与口径

| 位置 | 内容 |
| --- | --- |
| 报告页 | 元信息区一格"用量"；正文一节分阶段明细表（界面上不出现模型名） |
| `/dashboard` | 每条视频一列 token + 调用次数（**累计口径**，含导师提问与点评）；标题栏累计 |
| `/admin` | 全站卡片 + 分阶段/分用户明细 + 最近消耗 + 用户表 token 列 |
| `/health` | 全站聚合 JSON，供运维/监控抓取 |
| `/guide` | 公开说明估算规则 |

三处模板均以 `{% if usage and usage['calls'] %}` 守卫，无数据显示"—"或不显示，绝不伪造 0。

> **口径声明（界面已注明）**：本统计用于观察用量结构与异常消耗，**结算以 DashScope 控制台账单为准**；估算行会显示"估算"标记。

### 9.5 演示模式的行为（重要）

`LLM_MODE=mock` 时 `_mock_channels()` 直接造数，**`_complete()` 根本不被调用**，因此 `api_calls` 恒为 0、token 区块不出现。这是刻意设计：演示不得假装消耗额度。测试也因此必须用"直接驱动 `_track` + 落库 + 聚合"的单元式断言，而非页面文本断言。

### 12.1 窄屏适配：手机与电脑共用一套样式

需求："把 web 页面改一版手机可以适配的，手机、电脑都要能用"。约束决定了做法：无构建、无框架、全站只有一个 `style.css`（§12），所以**只能用纯 CSS 媒体查询 + 模板结构微调**；批注纸的视觉语言（纸底 / 墨字 / 朱砂 / 宋体标题 / 等宽数据）保持不变，窄屏是**重新排布**而不是换皮肤。

断点体系（全部写成 `@media screen and (max-width: …)`）：

| 断点 | 触发什么 |
| --- | --- |
| `1080` | 卡片栅格与账目条先折成自适应列，宽屏还不需要滚动 |
| `860` | 分数头改单列、总分区纵排、胶片带缩格；**宽表从这里开始横向滚**，不等挤到手机上才崩 |
| `680` | 手机主形态：顶栏品牌独占一行 + 导航等分铺满、页脚竖排、触控区放大到 44px 级、单列栅格、表格字号与内边距收紧 |
| `420` | 小手机：再收版心与字号、印章徽章缩小、维度头三列再压缩 |

`>1080` 不进入任何一条规则，**电脑端观感与改造前一致**（这是"手机能用但不得回退"的实现前提）。

**宽表统一交给 `.table-wrap`**：最宽的是用户表 9 列、全部视频表 8 列，`th` 又是 `white-space: nowrap` 的，撑破版心是手机端首要障碍。契约是——外层 `.table-wrap` 承担 `overflow-x`，模板用内联 CSS 变量给每张表一个最小宽度（`style="--table-min:900px"`），`.pin-first` 让首列（演讲名 / 用户名 / ID）`position: sticky` 吸左、滚动时不迷路，`.narrow` 用于列数少、不需要最小宽度的表。共 **15 张表**全部收进这个容器，滚动方向用容器内阴影提示。**新增表格时必须一起补这层包裹**，否则窄屏又会崩。

三个踩过一次就会反复踩的坑：

1. **特异性**：`.table-wrap > .sheet-table`(0,2,0) 高于基础层的 `table.sheet-table`(0,1,1)，所以 `width: max(100%, var(--table-min))` **只能写在断点里**；写进基础层会连带把电脑端的表也撑宽。基础层只留 `width:100%`。
2. **打印**：A4 打印视口只有约 794px，会命中 `860/680` 规则并盖掉 `@media print` 的排版。因此窄屏规则一律加 `screen` 限定，并在 print 块里把 `.table-wrap, .chart-scroll` 恢复成 `overflow: visible`（打印要整表铺开，不要滚动条阴影）。
3. **行内样式压制断点**：宽度写在 `style=""` 上永远赢过媒体查询。本轮把配额输入框、勾选框、页头弹性布局全部从行内搬进类（`.quota-used` / `.quota-limit` / `.pick` / `.head-flex` / `.head-main`），窄屏才能统一收回 100%。判断标准：**固定 `width` / `min-width` 必须进类**，`max-width`（如 `.meter` 的 420px、登录卡的 520px）可以留在行内——它的语义本来就是"窄屏自然收缩"。

**触摸与系统细节**：输入框字号 ≥16px 防 iOS 聚焦放大；`viewport-fit=cover` + `env(safe-area-inset-bottom)` 让页脚不被手势条压住；`touch-action: manipulation` 去掉双击缩放延迟；tap 高亮换成朱砂淡色；`@media (hover: none)` 关掉行高亮与卡片缩放（触屏上 hover 会"粘住"）；`a/button/summary/[tabindex]` 的 `:focus-visible` 给 2px 朱砂描边，手机键盘与遥控器都能看见焦点。

**图表在窄屏的两种处理**：趋势图的 `viewBox` 有 720 单位宽，等比缩到手机宽度时坐标轴文字只剩 4~5px，所以外面套一层 `.chart-scroll`，窄屏把 SVG 固定成 600px 宽**横向滚动**（与表格同一套心智）。雷达图反过来——它不该滚动，但 viewBox 缩放会把字号一起缩没，于是窄屏把 `.radar-label` 提到 15px、`.radar-sub`/`.axis` 提到 13px 补足。同时 `main._label_x()` 按"中文 1em"估宽，把标签的 `x` 夹回画布内：原先 7~8 字的长维度名（`流利度与连贯性`、`态势语与舞台表现`）贴着边界会被 `viewBox` 直接切掉，**这是电脑端就存在的问题**，现在宁可让标签向内压进网格区也不缺字。估宽用的 15 正好等于窄屏字号，两级不会再撑破。

**改模板时的红线**：页面上有 4 处内联脚本靠 CSS 选择器工作，重构样式不能动这些类名/属性——`progress.html` 与 `dashboard.html` 的轮询依赖 `#rail`、`#pct-text`、`#stage-line`、`.stage-list li[data-step]`、`tr[data-video]`、`.meter i`、`.stage-text`；`admin.html` 的 `randInto(id)`；`report.html` 的 `.time-chip[data-seek]` + `#player`。验证方式是 `python tests/selfcheck.py`（117）与 `LLM_MODE=mock python tests/smoke_web.py`（232）全绿，再加一次标签开闭计数自检。

## 13. 网页化配置（`/settings`）与热刷新

目标：`.env` 里的每一项都能在浏览器里看懂、改对、改完立刻生效，同时**不破坏"模型与 key 只认 `api_key.txt`"这条硬约束**；发给大模型的提示词也在这一页上可维护（§13.8）。

### 13.1 一张声明表驱动全部

`config.py` 的 `EnvField`（frozen dataclass）是唯一事实来源：`key` / 中文标签 / 控件类型（`secret·text·select·bool·int·float`）/ 对应的 `settings` 属性 / `hint`（框下说明）/ `note`（生效范围，如"影响新任务"）/ 默认值 / 可选值 / 关联的 `api_key.txt` 槽位 / 上下限与步进 / `scale`（字节存储按 MB 编辑）/ `clearable`。

`ENV_GROUPS` 把 **28 项**分 4 组：服务接入 3、评审通道 8、关键帧与微表情 7、站点与安全 10（`USER_UPLOAD_LIMIT` 归在最后一组，见 §8.2）。校验、写回、页面渲染、测试断言都读这张表——**新增一项只需加一行声明**。

同一个设置页上其实有**两张声明表、两条落盘链路**：本节讲的 `EnvField → .env`，和 §13.8 的 `PromptField → 提示词.json`。两者刻意不合并，原因写在 §13.8。

### 13.2 热刷新为什么可行

- `Settings` 的每个环境变量派生字段都写成 `field(default_factory=lambda: os.getenv(...))`；`reload()` 遍历 `dataclasses.fields()`，对**有工厂的字段**（判定用 `callable(f.default_factory)`）原地 `setattr`，`base_dir` / `rubric_file` 这类静态字段不动。
- `settings` 是模块级单例，全项目 100+ 处都是运行时属性查找 `settings.xxx`（没有 `lru_cache`，也没把模型名烤进长驻客户端），所以刷新后其后的请求与分析任务立刻用新值——**不重启、不重导入、进行中的任务不受影响**。
- `refresh_runtime()` = `load_dotenv(ENV_FILE, override=True)` 重灌 `os.environ` + 重算 `FILE_VALUES/FILE_MODEL`（`api_key.txt` 可能被外部编辑过）+ `settings.reload()`。`/settings/reload` 按钮就是它的 HTTP 入口，用于"手工改过文件但页面显示旧值"。

### 13.3 取值优先级与"回填值 ≠ 生效值"

优先级：**`.env` 里填写（网页写回）> `api_key.txt` > 内置默认**，`value_source()` 另可识别"环境变量"（进程级注入，如测试里的 `LLM_MODE=mock`）。

每行给页面两个值，这是本节最重要的设计：

| 字段 | 含义 | 去向 |
| --- | --- | --- |
| `value` | 当前**生效**值（按 `scale` 换算成人类单位） | 只渲染在右侧"当前生效"栏 |
| `raw` | 输入框**该预填**什么：仅当来源是 `.env` 才非空 | 渲染进 `input/select` |

若把生效值直接回填进输入框，管理员随便点一次保存就会把 `api_key.txt` 里的模型名钉死写进 `.env`，从此页面覆盖文件——违背硬约束。留空即"不覆盖"，页面用「来自 `api_key.txt` / 内置默认」徽章解释为什么框里是空的；下拉框也额外给一个"不覆盖 · 沿用上游"空选项，避免默认选中第一项而静默钉死。

### 13.4 校验与写回

- `write_env_file()`：逐行匹配 `KEY=`，**只替换命中的行**，保留原有注释、空行、键顺序与**换行风格**，新键追加末尾；先写 `.tmp` 再 `os.replace()` 原子替换。换行风格这条是踩过坑的：`splitlines()` 会丢掉行尾，若拼好文本后用默认 `newline=None` 写盘，Windows 会把整个 LF 文件翻成 CRLF——一次保存等于重写每一行，"保留格式"就成了空话。因此先读原始字节判定主导行尾（CRLF 数 vs 纯 LF 数），再 `write_text(..., newline="")` 按原样落盘。
- `save_settings()`：与 `read_env_file()` 比对，**只写真正变化的键**，返回变化列表用于"已保存 N 项（…）"提示；无变化时明确回"没有需要保存的改动"。
- `validate_env_updates()`：整表遍历（页面必然提交 28 项）。错误汇总成一句中文（`标签：原因`）；开关未提交即 `0`；密钥留空 = 不改，只有 `clearable` 且勾了 `__clear` 才写空（= 清除覆盖，回到 `api_key.txt`）；下拉留空 = 写空值"不覆盖"；`int/float` 按声明的 `low/high` 逐项卡区间；`QWEN_BASE_URL` 去尾斜杠；选 `whisper` 时补默认 `WHISPER_MODEL_SIZE`。**跨字段规则已经清空了**——旧版这里有一条"帧数下限 ≤ 上限"，下限夹取消后（§5.1.1）它没有作用对象了，与其留一段永远不会命中的代码，不如连字段一起删干净。
- **校验失败完全不写盘**：回显时把提交值标成琥珀色"待保存"徽章，与绿色的"当前生效"并列，避免"报错却以为改成了"。

### 13.5 页面与权限

- 三个入口统一走 `session_user()`：未登录 303 跳 `/login`，非管理员 403；导航栏"系统设置"只在 `role == 'admin'` 时出现。
- 密钥类（`DASHSCOPE_API_KEY` / `SECRET_KEY` / `ADMIN_PASSWORD`）用 `type=password` + `autocomplete=new-password` 的空框，右侧只给 `mask_secret()` 首尾掩码（`sk-1****…1234`），提示"留空表示不修改"。**整页 HTML 不出现明文 key**（冒烟用例直接断言真实 key 不在响应里）。
- 布局沿用 §12 的约定：`.rows` 单列整行、每组一张 `.sheet`、每行三栏（标识+键名 / 控件+hint / 生效值+来源徽章+note）；`data-reveal` 只有 7 级，组数用 `{{ [.., 7] | min }}` 夹紧；880px 以下降为单列；打印时 `.env-row` 不跨页、动作按钮隐藏。

### 13.6 管理员账号的双写

`ADMIN_USERNAME` / `ADMIN_PASSWORD` 同时活在 `.env` 与 `users` 表里，因此：先用 `_admin_account_issues()` 在**写盘之前**挡住格式错、重名、口令 < 6 位；写盘成功后由 `db.sync_admin_login()` 改名（含查重）或回写口令 hash。改 `SECRET_KEY` 会让所有旧 cookie 失效，保存响应用 `_set_session()` 给当前管理员重发，避免"改个设置把自己锁在门外"。

### 13.7 测试隔离

`ENV_FILE = Path(os.getenv("ENV_FILE") or BASE_DIR / ".env")`。`smoke_web.py` 在 import `app.*` **之前**把 `ENV_FILE` 指到 `data/_websmoke/_websmoke.env`；`selfcheck.py` 第 9 节把 `cfg.ENV_FILE` 猴子补丁到临时文件，`finally` 里还原并快照/恢复 `os.environ` 后 `refresh_runtime()`。两处都保证自动化测试绝不写坏用户真实的 `.env`。

提示词那份是**同一个坑的第二个实例**：`PROMPTS_FILE` 同样是模块级求值（§13.8），所以 `os.environ["PROMPTS_FILE"]` 必须在 `from app import …` **之前**设好，事后改环境变量无效——写晚了测试会覆盖仓库根的 `提示词.json`。两个脚本都已把它指到自己的临时目录。

### 13.8 大模型提示词：第二张声明表与差量落盘

需求："把大模型相关的提示词也放到管理员的页面，管理员可以修改"。做法是在 `.env` 之外另开一条链路：`prompts.py` 声明 **19 块**提示词，分 **7 组**（共用规则 3 / 文字通道 2 / 画面通道 3 / 语音通道 2 / 语音转写 1 / 反馈叙述 3 / 导师提问 5），在同一张设置页上以 `textarea` 呈现。

**为什么不塞进 `.env`**：`config._quote_value()` 与 `validate_env_updates()` 会把值里的换行压成空格（`.env` 的语义是"一行一个标量"），多段长文本进去就毁了；而且提示词是**内容资产**、环境参数是**运行开关**，两者变更频率、回滚方式、评审人都不一样。分文件后 `git diff 提示词.json` 只出现提示词改动，改配置也不会顺手覆盖提示词。

`PromptField` 的字段：`key`、中文 `label`、内置 `default`、`hint`（框下说明）、`note`（改动风险，如"删掉它模型会开始凭印象打分"）、`tokens`（本块允许的系统占位符）、`strict_braces`（是否禁止其它花括号）、`must_contain`（必须保留的字面串，用于守 JSON 键名）。

四条关键语义：

1. **差量存储**：`normalize()` 后与 `DEFAULTS[key]` 相同的块**不写盘**。文件里只有管理员真正改过的块，`_meta` 记版本与时间；改回原样再保存，这块自动从文件里消失、回到内置默认；删掉整个文件 = 全部回默认。`save()` 写的是**完整快照**，所以一次提交就能同时完成"改 A、清空 B、原样保留 C"。
2. **留空 ≠ 删除要求**：整块清空只表示"用内置默认"。想让系统不再评价某项，得把该块改写成一条明确的"不评价"指令——页面上把这句话写了三遍，因为这是最容易误解的地方。
3. **占位符是接口不是文案**：`{name}` 由运行期注入（转写文本、维度键名、JSON 结构、帧数、时长预算…）。`render()` 用**单次** `_TOKEN_RE.sub`，替换结果不再二次扫描，所以转写里出现字面 `{keys}` 不会被展开。`validate()` 双向卡：声明的占位符必须都在（否则模型收不到材料）、`strict_braces` 块不许有额外 `{…}`（防把占位符当排版符号）、`must_contain` 守住写回报告的 JSON 键名、单块上限 6000 字。**任一块不过 → 整份不写盘**，并把草稿原样退回页面、在对应格子标出缺了哪几个。
4. **保存即生效，无需重启**：`analyze.py` 每次拼请求时才 `prompts.get()/render()`，`qwen.py` 的 ASR 指令同理，所以新的分析任务立刻用新提示词（正在进行的那次不变）。生效值与差量都只经由 `overrides()` 的 `(mtime_ns, size)` 缓存读，页面/引擎/测试看到的是同一份真相。

**一处必须写进文档的事实**：`system` 提示词历史上**只作用于文字通道**——`qwen.vision()` / `qwen.audio()` 形参里有 `system`，但 `analyze.py` 从不传，画面与语音通道的规则全部写在请求正文的块里。页面文案按这个事实写，`selfcheck` §11 也用一个 `_Spy` 客户端把三条通道实际送出去的正文钉住（含"画面/语音不重复挂 system 角色"这条反向断言），避免将来有人以为改了 `system` 会同时影响三路。

代价记在 §16：提示词一改，新旧报告的**判分口径**可能就不同了，而分数聚合规则与标准版本号都没变，系统不会提示这件事。已落库的历史 `payload` 不受影响，但"历次对比"的可比性由管理员自己负责。

## 14. 部署与运维

### 14.1 启动方式与管理员入口

```powershell
cd d:\heyun\speech_assist
pip install -r requirements.txt          # 需要 ASR_ENGINE=whisper 时再 pip install faster-whisper
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
# 浏览器打开 http://127.0.0.1:8000
```

**只能单进程跑，不要加 `--workers`**：分析队列、抽帧/分析线程池、千问在途请求闸门都在进程内（§14.4）。开两个 worker 等于两套互不知情的池子——同时分析路数翻倍、去重失效、`/health` 只反映其中一个进程。真要横向扩展，得先把队列搬到外部（独立 worker 进程 + 共享库），这属于 §1.2 的非目标。

首次启动自动 `init_db()`（建表 + 列迁移 + 建管理员）。管理员口令来自 `.env` 的 `ADMIN_USERNAME/ADMIN_PASSWORD`（默认 `admin/admin123`，**生产必须改**）。

管理员入口**就是同一个登录页**，没有隐藏后台地址：

1. 打开 `http://<服务器>:8000/` → 点首页的「管理员入口」（或直接「登录进入系统」），用 `.env` 里那对管理员用户名/口令登录；
2. 登录成功后导航栏出现 **「管理后台」**（`/admin`）与 **「系统设置」**（`/settings`）。普通用户看不到这两个入口，拿到 URL 也是 403——角色只认数据库，伪造签名载荷无效（§7.2）；
3. 改管理员口令有两条等价路径：`/settings` 里填新口令保存（`db.sync_admin_login()` 会同步回写 hash，§13.6），或在 `/admin` 用户表里对管理员自己用「重置口令」；
4. 普通用户账号全部在 `/admin` 的「账号开通」面板产生——逐个录入或 Excel 批量导入（§8.1）。网站首页和 `/register` 都不提供注册入口，访问 `/register` 会被送回登录页并说明去哪拿账号。

### 14.3 常见故障定位

| 症状 | 先看 | 处置 |
| --- | --- | --- |
| 报告全是"演示模式" | `/health` 的 `mode`、`key_source` | 检查 `api_key.txt` 是否被读到、`LLM_MODE` |
| 分析失败：ffprobe 失败 | 错误文本 + `ffmpeg` 是否为 true | 装 ffmpeg 到 PATH；确认文件是真视频（手机可变容器需转码） |
| 分数被大面积下调 | 报告"质控记录" | 逐条读，通常是证据未命中或转写不可信 |
| 转录很慢 | `/health` 的 `asr_engine` | 本地 whisper 在 CPU 上较慢，改回 `qwen` 或换 `tiny/base` |
| 卡在"分析中" | 重启后是否变"已中断" | `reset_stale_jobs()` 已处理，点重试 |
| 403/额度类报错 | 质控 + `api_key.txt` 余额 | 换模型名或充值；这类错误**不会**被降级链掩盖 |
| 用户反馈"传不上去" | 后台该账号「上传次数」面板的 `已用/上限`、全局 `USER_UPLOAD_LIMIT` | 大多是配额用尽（**不是故障**）。提示语会写明"上传次数已用完（3/5）"还是"该账号已被管理员停止上传"：前者点「清零已用」放行，后者把上限填回正数或「跟随全局」；若确实没到额度却传不上，那是体积被 `MAX_VIDEO_MB` 拒了（§8.2） |
| 关键帧张数比预期少 | 报告页底部胶片带的张数与时间戳、`videos.duration` | 正常：张数 = `round(时长 / FRAME_INTERVAL)`，只封上限不抬下限（§5.1.1）。10 秒视频只有 2 帧是**设计行为**，不要为了凑数去改小 `FRAME_INTERVAL`——那会把所有长视频的 token 一起放大 |
| 报告里没有正脸率/朝向指标 | `/health` 的 `face_metrics` 与 `face_metrics_note`、质控记录里的降级理由、`videos.frontal_ratio` 是否为 NULL | 四种正常情形：未装 opencv、装成 5.x（`note` 会点名 `CascadeClassifier` 缺失）、`USE_FACE_METRICS=0`、人脸检出率 < `FACE_MIN_DETECT`。**这是设计行为**——"拍不清"不该被当成"不看镜头"扣分，别为了出数字去拆门限（§5.1.2） |
| 设置页显示的值和 `.env` 里写的不一样 | 该行的**来源徽章**与"生效值" | 正常：徽章是 `api_key.txt` 或内置默认，输入框本来就是空的（回填值 ≠ 生效值，§13.3）。若确实手工编辑过 `.env`，点页面底部「按磁盘上的 `.env` 重新加载」 |
| 保存后没生效 | 跳转提示里的"生效说明"、`/health` | 看是否被校验拦下（页面顶部有"未保存"和"待保存 N 项"徽章就是没写盘）。路径类 `DATA_DIR`/`ENV_FILE` 故意不上网页——改了会让库和文件错位，只能编辑 `.env` 并重启进程 |
| 多人同时用时页面莫名转圈（分析却没满） | `/health` 的 `concurrency`：`running` 是否远小于 `analyzers`、`web_threads` 是否等于 `WEB_THREADS` | 是网页线程排队，不是分析排队：调大 `WEB_THREADS` 后**重启进程**（§14.4）。若 `running == analyzers` 则是正常排队，让用户等或调 `MAX_ANALYZERS` |
| 大视频上传被拒 413 | 反向代理（nginx）的 `client_max_body_size` | 代理默认 1 MB 会先拒掉，应用侧 `MAX_VIDEO_MB` 根本没参与。改代理到 ≥ `MAX_VIDEO_MB`（§14.4） |

### 14.4 10 个用户同时使用：瓶颈在哪、要什么配置

**三层额度各自独立**，都可在 `/settings` 改，`/health` 的 `concurrency` 实时给出"配置值 + 在途值"：

| 层 | 实现 | 默认 | 满了会怎样 |
| --- | --- | --- | --- |
| 网页请求 | anyio 线程闸门，启动时 `tune_thread_pool()` 上调到 `WEB_THREADS`（只增不减） | 64 | 页面转圈、上传卡在进度条——**表现是排队而不是报错** |
| 视频分析 | `pipeline` 的 `ThreadPoolExecutor(max_workers=MAX_ANALYZERS)`，空闲时可按新配置重建 | 10 | 新任务排队，详情页显示"等待中"，`running == analyzers` |
| 千问请求 | `qwen.GATE`（`BoundedSemaphore(MAX_LLM_REQUESTS)`） | 20 | 单路分析的各阶段串行等网络，进度条停在某个阶段 |

为什么分析路数（10）与模型在途数（20）不相等：一路分析里"文本 / 视觉 / 音频"三类请求可能先后或交错发出，10 路都挤在模型侧时给 2 倍余量，既提高吞吐又不至于 10 路同时打满网关拿到 429——**429 类错误不会被降级链掩盖**（§10），一旦触发就是显式失败，所以宁可保守。

CPU 花在哪（决定了下面的核数建议）：一次 2–3 分钟视频的分析里，本地计算主要是 ① ffmpeg **逐点 seek 抽帧**——每帧一个独立进程，从最近关键帧解码到目标时刻，成本随**张数**（≈ 时长的 1/5，封顶 100）与容器 GOP 长度走，而不是全片解码 ② opencv Haar 逐帧测量（受 `FACE_MAX_FRAMES=120` 封顶）③ mjpeg 编码关键帧。real 模式下网络等待更长，但那段时间 CPU 是空的——**所以按并发峰值配 CPU，而不是按平均占用**。

**推荐配置（10 个用户同时操作、约 200 个视频/天）**：

| 项 | 建议 | 依据 |
| --- | --- | --- |
| CPU | **8–16 物理核**，≥2.4 GHz | 10 路里真正同时抽帧的通常 3–5 路；ffmpeg 与 opencv 各自还会用多线程 |
| 内存 | **16 GB 起**，32 GB 从容 | 进程基线约 300 MB（含 opencv）；每路分析主要占抽帧图与响应 JSON（数十 MB 级），10 路 + 64 网页线程远不到 8 GB。**若 `ASR_ENGINE=whisper`**：`small` 另占 ~2 GB、`medium` ~10 GB，那时才需要 32 GB 或改回云端 ASR |
| 磁盘 | **NVMe 200 GB+** | 上限 `MAX_VIDEO_MB=500`，实测 2–3 分钟手机视频 20–60 MB；抽帧产物按"每 5 秒一张 jpg（封顶 100 张）+ 16k 单声道 wav（约 32 KB/s）"计，2–3 分钟约 3–10 MB，15 分钟顶格约 35 MB。200 条/天留半年 ≈ 20 GB 视频 + 数 GB 产物，SQLite（WAL）本身常为几百 MB。**必须是本地 SSD，别放网络盘**：WAL 靠 `mmap`+`fsync`，网络文件系统上写入抖动会直接变成网页卡顿 |
| 系统 | Ubuntu 22.04 或 Windows Server 2022，ffmpeg 7.x 在 PATH | 纯 seek 抽帧是 ffmpeg 最稳的用法（旧版为 `select='gt(scene,..)'` + `yuvj420p` 做过的一串版本兼容降级已随场景检测删除），但装完仍先 `/health` 看 `ffmpeg: true` |
| GPU | **不需要** | ASR 走云端 `qwen3-asr-flash`，视觉与文本判分都在千问侧；本地只有 ffmpeg + Haar 级联，CPU 更省运维 |
| 网络 | 上行 **≥30 Mbps**，并让 `MAX_VIDEO_MB` 与带宽匹配 | 500 MB 在 30 Mbps 上行约需 2.5 分钟；若出口只有 10 Mbps，建议在设置页把上限调到 200 MB（热生效）。10 人同时上传时瓶颈在网络，调 `WEB_THREADS` 无用 |
| 部署形态 | nginx 反代 + `client_max_body_size 512m` + **单个** uvicorn 进程 | 代理默认 1 MB 会先 413；多 worker 会分裂队列（§14.1） |

上线前的 5 分钟容量自检：`curl http://<host>:8000/health`，连着提交几个视频后看 `concurrency` —— `running` 应随任务数增长并在 `analyzers` 处停住；`llm_in_flight` 必须 ≤ `llm_requests`；`web_threads` 应等于 `WEB_THREADS`（不等说明没重启，该项标注的就是"重启服务后生效"）。日常容量告警只需盯 `running == analyzers` 出现的时长占比。

### 14.5 云上部署包（`deploy/`）

上面是"应该怎么做"，`deploy/` 是"已经写好怎么做"。八份产物分两半：**服务器上跑的**七份（含本手册自身）+ **本地打包用**的一份。形态由一条事实决定——**本仓库不是 git 仓库**，所以没有 `git clone/pull` 这条路，发布链路只能是 `package.ps1 → scp → 解压 → install.sh`（幂等，可反复重跑对齐配置）。

| 文件 | 跑在哪 | 关键设计点 |
| --- | --- | --- |
| `package.ps1` | Windows 本地 | **白名单**打包（`app/ deploy/ docs/ tests/ requirements.txt 评价标准.txt .env.example`），先删编译产物，再把 `deploy/` 下模板统一换成 LF，然后断言包里**不得出现** `api_key.txt` / `.env` / `speech.db` / `*.wav` / `data/`；打完立刻回环解压，验证中文文件名存活与 `.sh` 无 CR 字节 |
| `env.production` | 变成 `/opt/speech-assist/.env` | 2C2G 收紧版：`MAX_ANALYZERS=2`、`MAX_LLM_REQUESTS=4`、`WEB_THREADS=32`、`MAX_VIDEO_MB=200`、`ASR_ENGINE=qwen`。每处偏离本地默认值的取值旁边都写了理由，`/settings` 改完后这层注释仍随 `.env` 保留 |
| `speech-assist.service` | 渲染进 `/etc/systemd/system/` | 单进程（**绝不能加 `--workers`**，队列与信号量都在进程内，见 §14.1）、`Restart=always`、`User=speech`；沙箱只到 `ProtectSystem=full` 而非 `strict`——应用要往 `BASE_DIR` 写 `.env` 与 `提示词.json`，`strict` 会让保存功能静默失败；也**不用** `ProtectHome`，因为密钥就在应用目录下 |
| `nginx-speech-assist.conf` | 渲染进 `/etc/nginx/conf.d/` | `client_max_body_size` 由 `MAX_VIDEO_MB + 20` 派生，所以调上传上限只需改一处；`/health` 只允许 `127.0.0.1`（它带模型名与 token 用量）；`/static` 直接 `alias` 出文件，`/videos/*/{play,asset}` 必须反代——会话保护 + 应用自带 `Range` 流式（§7.4） |
| `install.sh` | 服务器 | 十二步：同步（`rsync --delete` + exclude 保护 `.env`/`api_key.txt`/`data/`/`.venv`）→ 断言 `评价标准.txt` → apt 依赖 → 探测阿里云内网 pip 源 → 内存 <4 GiB 建 2 G swap → 建 `speech` 账号 → venv + Python≥3.10 断言 → 生成 `.env` → 权限 → systemd → nginx（移除 Ubuntu default 站点）→ `/health` 轮询验收。渲染后 grep 自己有没有 `--workers`，有就中止 |
| `update.sh` / `backup.sh` | 服务器 | 升级先备份再同步再健康检查；备份用 Python `sqlite3` 的 backup API（WAL 模式下裸 `cp` 会拿到主库与 `-wal` 不一致的半份快照），备份完立刻对新库跑 `PRAGMA integrity_check`；滚动保留并给出 cron 建议 |

**"两人档"是对 §14.4 的刻意降级**，不是那一份推荐作废：3 Mbps 出网 ≈ 375 KB/s，两个用户各自回看一次上传的视频就能把带宽占满，所以先按并发 2 配 CPU 与内存（实测 2 并发峰值 500–600 MB，2 GiB 有余量，还挂 swap 兜底），把带宽限制写进部署手册 §10 的已知限制表而不是假装不存在。换大机器之后重跑一次 `install.sh` 即可让 nginx 与新配置对齐。

两个只有跑过才会发现的坑（已修，但值得留在文档里，因为它们都是**静默失效**型）：

1. `api_key.txt` 同时被打包白名单排除（防泄密）和被 rsync exclude 保护（防覆盖误删）——两条正确规则叠加的结果是首次部署它永远落不到 `/opt/speech-assist`，系统于是**一路以演示模式产出假报告**。修法是在 `install.sh` 里显式从发布目录 `install -m 600` 过去，并把手册第 3 步写成"先 `cp /root/api_key.txt <发布目录>/`"。
2. `ADMIN_PASSWORD` 的语义是"账号不存在时用它建号"（`db.init_db`），改哈希的唯一路径是 `/settings` 保存时调 `db.sync_admin_login`（`main.py`）。所以"编辑 `.env` 再重启就能改口令"是不成立的，而改 `ADMIN_USERNAME` 再重启会**多出第二个管理员**而不是改名。更麻烦的是 `videos.user_id` 与 `evaluations.video_id` 都是 `ON DELETE CASCADE` 且每连接 `PRAGMA foreign_keys=ON`——救口令时绝不能 `delete from users`，只能 `UPDATE password_hash`（手册 §11.1 给了完整脚本）。同一段生成逻辑还按 dotenv 的实测规则处理口令里的 `#` 与引号：`x#y` 原样、`x #y` 会被截成 `x`、`"ab` 会让整行消失，因此能安全加引号时自动加，不能时显式告警。

约定：

- 两个脚本都用 `DATA_DIR=data/_selfcheck|_websmoke` 做**完全隔离**并启动时清空，绝不触碰正式库。
- 涉及设置页的用例还必须隔离 `ENV_FILE` **与 `PROMPTS_FILE`**（`smoke_web` 用环境变量、`selfcheck` 第 11 节用 `os.environ.setdefault` 并保证在 `import app.*` **之前**）——这两份都是要**写盘**的，若漏掉隔离，测试会把真实 `.env` 覆盖成测试值、把开发机上手工调好的配置悄悄钉死，或直接改写仓库根的 `提示词.json`。同理，设置页断言只信临时文件与运行时对象，不信仓库里的 `.env` 内容。
- 断言以"行为 + 契约"为主（维度数一致、分数区间、总分自洽、越权必 403），文案断言只用稳定关键词。
- token 记账必须走单元式断言（见 §9.5）：`_track → usage_summary → _flush_usage / add_usage → token_usage` 各验一次，含估算标记、阶段分组，以及"累加不覆盖分析统计"这条（另起 client 记账后，分析阶段的 token 必须还在）。
- 冒烟里含**反向断言**（`absent=`）：落地页不得再出现"评分要点/关于分数/怎么用"，用来守住"首页要很干净"这条需求。
- 本地跑这两个脚本要显式 `$env:LLM_MODE='mock'`：仓库目录里有真 `api_key.txt`，默认 `auto` 会真调千问（慢且烧额度）。**这条不只是省钱的建议——漏掉它会拿到不可复现的红灯**：有一次 `selfcheck` 未加 mock 跑出 84/85（退出码 1），失败项却被管道缓冲吞掉看不见；同一份代码重定向到文件、加 `LLM_MODE=mock` 后稳定 85/85（当时的总数，现基线见上表）。PowerShell 下把输出重定向到文件再 `Get-Content -Tail`，直接用 `... | Select-Object -Last N` 会因管道缓冲看不到任何进度。
- 三层并发额度**只从 `/health` 与 `/health.concurrency` 断言**，不在测试里直接读 anyio：`anyio_thread_tokens()` 依赖"当前在事件循环内"，而 FastAPI 的同步 `def` 路由会被丢进工作线程执行，读回来恒为 0。这条回归真实发生过——`web_threads >= 64` 首跑即失败，修的是路由（改 `async`）而不是断言。
- 抽帧探针视频仍用**白/黑/红**三段纯色 + 测试图。历史上这套颜色是为"ffmpeg 的 `scene` 分数按亮度直方图计算、红↔绿这类等亮切换只有 0.2x 过不了门限"选的；场景检测整体删除后（§5.1.1）颜色对抽取算法不再有影响，保留的理由是：① 硬切仍然是最容易被"抽帧丢掉/抽成空白"的采样位置，能真实压力 512 字节体积门槛；② 若将来重新引入内容感知采样，夹具不会因为等亮切换而误报故障。断言口径也已从"是否对齐 3/6/9 三刀"改成**"间隔是否恒定"**——旧断言守的是场景检测的功能，新断言守的是等距这个不变量，两者不可混用。
- 配额类用例必须**双向**断言：既验"用尽即拒"（响应里带 `已用/上限` 文案、且**磁盘上没有多出文件**），也验"放行路径"（清零、删一条返还、单独上限、填 0 封禁、非法值不改库）。只测拒绝会漏掉最常见的运维动作，只测放行会把"额度形同虚设"当成正常。

## 16. 已知限制与演进方向

| 限制 | 影响 | 可选演进 |
| --- | --- | --- |
| 音频只取前 15 分钟 | 超长演讲后半无评价 | 分段摘要式判分或按维度采样 |
| SQLite + 线程池 | 单进程有效，多 worker 会争抢 | 换 Postgres + 独立 worker（`enqueue` 已是唯一入队点） |
| 微表情只能测"头部朝向"，测不了视线与瞬时表情 | Haar 级联判不了真实注视方向，眨眼频率在稀疏静态帧上根本不存在；"乱瞟""表情不自然"仍主要靠模型看图主观判，指标只作交叉核对 | 换视线/表情单元级模型（MediaPipe Face Mesh、OpenFace 的 AU），或按需求追加一次独立的特写帧 VLM 精判请求（成本翻倍，且要重新定义与历史分数的可比口径） |
| 客观指标不参与判分 | 正脸率再低也不会自动扣分，只留"分数保持不调整"的冲突提示 | 若要让它进分数，必须先定"多少正脸率对应多少分"的标定集，并与评分标准同步升版本号，否则历史对比失真 |
| 设置页热刷新是"逐字段 `setattr`" | 多 worker 部署下各进程配置会不一致；保存瞬间正在执行的任务可能读到新旧混合的字段（同一批校验过的跨字段值仍自洽） | 与"SQLite + 线程池"同源：改成独立 worker + 配置版本号，任务领取时锁定一份配置快照 |
| 提示词可由管理员改写，但不参与版本指纹 | 改一句提示词就可能改变判分口径，而 `rubric.version` 与聚合规则都没变，历史对比不会提示"口径已改"（§13.8） | 给提示词快照也升一个指纹（如覆盖文件的 hash），存进 `evaluations.payload`，对比时发现不一致就明确标注"两次分析所用提示词不同" |
| 复发检测靠描述文本指纹 | 同义改写算两条 | 用 embedding 相似度聚类 |
| token 估算为粗规则 | 与实际计费有偏差 | 统一改用 `usage` 或引入 tiktoken 校准 |
| 单语言假设（英语演讲 + 中文反馈） | 其他语种词密度阈值需调 | 阈值按语言分支 |
| 无邮件/找回密码、无审计日志 | 运维可观测性有限 | 增加操作日志表与 SMTP |

## 附录 B：为什么这样设计（三句话总结）

1. **把"判断"和"裁决"分开**：模型只做带证据的单项判断，分数由可复现的确定性规则裁决，系统才可信。
2. **把外部依赖当不可靠来设计**：降级链、分阶段刷库、重启自愈、可信度闸门、演示模式，都是为了"任一环节失败也不静默骗人"。
3. **把口径写进界面**：`/guide` 与质控记录让使用者随时看到"分怎么来的、转录走的本地还是云端、token 怎么算的"，可解释性优先于好看。
